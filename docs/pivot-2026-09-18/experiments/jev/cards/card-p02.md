A step can cap its session's context: a `context:` key carried on the engine's task and turned into Claude Code's `--autocompact` — agent-engine, agent-workflows, the shipped folders, and the key's obligations in the apps

Measured 2026-09-18 over 234 worker sessions (docs/pivot-2026-09-18.md §1, Finding 1; docs/pivot-2026-09-18/experiments/cost/corpus.py and whatif.py): workers get Claude Code's one-million-token window and not one session ever compacted. The median session peaks at 173k tokens of context, the 90th percentile at 441k, the largest at 831k; three quarters of all input tokens were spent in calls carrying more than 200k; every token that enters a session is read again about 130 times. A cap at 200k would have saved at most 17% of all spend, at 150k about 22% — upper bounds, since compacting costs something and loses detail. The knob exists: `claude --autocompact <auto|tokens>` ("Auto-compact window size (auto, or 100k–1M tokens)", in `claude --help` on 2.1.277), and the environment variable `CLAUDE_CODE_AUTO_COMPACT_WINDOW`. Nobody has measured it on a `--bg` session.

Read CLAUDE.md (the rules the code keeps: the engine is finished, and "a knob on the workload is a field carried on the task and read by a runner, never a callback into `decide`"; the Kubernetes test for a new task field — `resources.limits` is the precedent), then packages/agent-engine/src/facade.ts (`TaskSpec`, and how `file()` refuses a bad `effort` or `permissionMode` BEFORE a task is journalled), src/domain.ts (the `filed` event), src/engine.ts (how a task's fields reach the runner), src/runner.ts (the `claude --bg` argument list and its comments on variadic flags that swallow the prompt — `--tools`, `--worktree [name]`, `--remote-control [name]`), src/runner-detached.ts (`claudeDetached`, `codex`), src/cli.ts (`ae file`'s keys), then packages/agent-workflows/src/workflow.ts (`STEP_KEYS`, `STEP_KEY_MEANINGS`, how `effort:` is checked against the harness the step runs on), src/runner.ts (where a step's keys become a task), and the three obligations of a new step key outside the package, as CLAUDE.md lists them: `KINDS` in apps/api/src/builder.ts, `WorkflowStepSpec` and `specOf` in apps/api/src/workflows.ts, apps/web/src/lib/api.ts's mirror with `UNSET` beside it in apps/web/src/lib/builder.ts.

What to build:

1. MEASURE FIRST, and let the measurement decide the rest. File a real `claude --bg` task with `--autocompact 100k`, make it read enough to pass 100k tokens (a dollar or so), and record what happens: does the flag take effect on a `--bg` session at all; does the transcript show the compaction; does the session carry on working afterwards and still sign off through `StructuredOutput` with a `--json-schema`; does a later `--resume` of that session with the same flag reuse the prompt cache or rebuild it; does the engine's usage reading (`transcriptUsage`) still count the attempt right across the compaction. Write what you saw, with the CLI version, into packages/agent-engine/docs/open-issues.md. If the flag does nothing on `--bg`, try the environment variable on the spawned process, and say which works. If neither works, stop there: sign off `blocked` with the measurement, and build nothing.

2. The engine: a task field for the cap (propose the name; a number of tokens), validated at `file()` — refused by name when it is not a whole number in the range the harness takes, and refused on a harness that has no such knob (`codex`, and any `HarnessSpec` that does not declare one), in a message that says what to do. The `claude` runner turns it into the flag, placed where no variadic flag can swallow it or be swallowed; `claude-detached` too if `claude -p` takes it — measure. `decide` does not learn of it. `ae file` takes the key and `ae show` prints it.

3. agent-workflows: a step key, `context:`, written as a person would write it (`200k`, `150000`), parsed once into tokens, refused by name outside the range and on a harness without the knob, rendered back by `renderStep` as it was written or in one canonical form — say which. It reaches the task where `effort:` does. The key's three obligations in the apps, and the board shows the key on a step as it shows `effort`.

4. One value for a session's whole chain: a retry, a round or a `respond` that continues a session is filed with the same cap as the session it continues. (A run that lands beside this one pins the same rule for the closeout schema; if it has merged, join its test rather than writing a second.)

5. The shipped folders: only if step 1 showed a compacted `--bg` session carries on and signs off, give every agent step of workflows/dev, dev-build, dev-planned, dev-planned-build and ui `context: 200k`, with the comment saying why in a line. Turbo does not see workflows/, three tests pin those folders, and workflows/ui is the package's folder file for file: CLAUDE.md says what to run and what to copy. If step 1 left a doubt, leave the folders alone and say in your closeout what the owner should decide.
