Agents on the board: a page that lists the agents beside the workflows, and a form that creates and edits one — agent-workflows writes the file, the api serves it, the web app draws it

The agent refactor (`f937d12`) made an agent a file of its own: `<workflows dir>/agents/<name>.md`, role keys and a `description:` in its frontmatter, its instructions as the body, named by a step with `agent:`. The board can show the agent a node names and edit the node; it cannot show or edit an agent. features.md's *What it leaves* says so. This is the first slice of the product's face in docs/pivot-2026-09-18.md (§6, P9): "Create an agent" is a form — a name, what it is responsible for, what it may reach, how careful — that writes the markdown. Read §3 of that document for the model: a step is a logical NODE of a workflow, and an agent is ONE kind of thing attached to a node; word nothing as if a step were always an agent.

Read CLAUDE.md (the apps/web lines, React Aria and `routeLink`, the e2e's rules, the three obligations of a key), then packages/agent-workflows/src/workflow.ts (`AGENT_KEYS`, `loadAgents`, `agentsDir`, the refusals in an agent file, `renderStep`), src/runner.ts (`writeWorkflow`: where it may write and why, its stale-write and link refusals, how it removes what it no longer lists), apps/api/src/builder.ts and src/workflows.ts (`KINDS`, `versionOf` — which already versions the agents a folder names — `judgedWith`, the PUT of a workflow), apps/web/src/routes/workflows*.tsx, the builder's components (`WorkflowBuilder.tsx`, `StepForm.tsx`, `StepNode.tsx`), apps/web/src/lib/builder.ts, and apps/web/test/e2e/run.ts (`PAGES`, the seeded store, the `builder-agent` page the refactor added).

1. The package writes an agent, as it writes a workflow: one function, one writer. It renders an agent file from a draft (the inverse of the agent parser, as `renderStep` is of the step parser — a round-trip test over every shipped agent), writes only where `writeWorkflow` may write, refuses by name what the parser refuses (a wiring key, `agent:`, a bad value, a name that is not a file's name, a symlinked target), refuses a stale write against a version, and refuses to REMOVE or RENAME an agent that any step of any folder beside it still names, saying which steps. A schema an agent's `output:` names travels with it as `writeWorkflow` carries a step's.

2. The api: list the agents of each place the board already lists workflows from (the repository's, and yours in the home store), each with its description, role keys, body, version, the steps that name it, and its error when it does not read; read one; create or replace one; remove one. Refusals are 4xx with the package's words. Nothing here touches a run: an agent edit changes only what a LATER `wf start` freezes, and the page says so.

3. The web app: an Agents entry in the menu and an Agents page — a list, and a form for one agent: its name, its description ("use this when…", the line a dispatcher will read later), model, effort, context, permission mode, tools and denied tools, remote, its result schema, and its instructions in a text area that is comfortable for a page of prose. It shows which nodes of which workflows use the agent, as links. A node's form in the workflow builder links to its agent's page. A repository's agents that the board may not write are shown read-only, as such workflows are. Build on the app's React Aria components; the shadcn skill's notes in CLAUDE.md apply.

4. The e2e draws the page and the form in both themes: a line in `PAGES`, a seeded agent, a create, an edit, a refusal on purpose on a page of its own (CLAUDE.md: the watch counts every 4xx), and the store put back before the page ends.
