# P3, reach and connections — a plan set aside

> The packages were renamed on 2026-09-23: `agent-engine` is now `packages/agent-runtime`, and `agent-workflows` `packages/agent-orchestrator`. This document is history, and keeps the names it was written with.

*Planned on 19 September by run `what-an-agent-may-reach-is-d-kma1` ($4), and not built.* The owner, at its gate: the
mailbox was only ever an example; a connection registry, a fake mail server and a fence of deny rules (or a proxy) are
too much for now — "just keep it simple". What they want first is an agent's configuration shaped after the A2A
protocol's Agent Card. This plan is kept because its reading of the code is worth the four dollars: what the engine's
`mcp` field does and cannot do, why a step's server set is exact only in a folder run, why the deny list is the fence
and `tools:` is not, and why a worker's secret is no better off. Read it before anyone connects a real account.

---

A plan for P3's first slice: `reach:` declares what a node may touch, a per-person connection registry under `~/.agent-workflows/connections/` holds how to start each MCP server and classes each of its tools read/draft/send, the filing site turns a step's `reach:` into an exact `mcp` set plus `mcp__<conn>__<tool>` deny rules on the engine's task, and a step that reaches a `send` class is refused at load unless it waits on a gated step. Everything runs against a fake mailbox server in fixtures; no Gmail, no OAuth, no token. The engine is unchanged. Three corrections to the brief's account of the code are in `approach`. The plan is gated: the seven decisions are the owner's, and `needs` lays each out with a recommendation and what was rejected.

## Needs

WAITS FOR APPROVAL OF THE PLAN. Seven decisions, each with my recommendation, what I rejected and why. Answer them with `wf approve <run> plan --message …` (or send the plan back with `wf retry <run> plan --message …`).

(1) THE DECLARATION. Recommend: a new key `reach:` on a step AND on an agent (`AGENT_KEYS`), a comma list of `<connection>.<class>`, e.g. `reach: mail.read, mail.draft`. Classes are exactly `read`, `draft`, `send`. A step's own `reach:` replaces the agent's, as every other key does. Refusals at load: a value that is not `<name>.<class>`; a class not in the three; a duplicate; `reach:` on a `harness: codex` step (see 3); `reach:` on a step whose `workspace:` is not `folder` (see the second correction in `approach`). It honours the three obligations outside the package (`KINDS`, `WorkflowStepSpec`/`specOf`, the web mirror + `UNSET`). REJECTED: agent-only — an agent is reusable across teams and the reach of "the drafter" differs per team, and the key must also be readable on the step page and refusable per step; `needs:` as the word — it collides with the closeout's `needs`; a nested YAML map (`reach: {mail: [read]}`) — the parser is line-and-comma throughout and `renderStep` would have to grow a second shape.

(2) THE REGISTRY. Recommend: `~/.agent-workflows/connections/<name>.json` (under `WF_ROOT`, like `runs/` and `inbox/`), one file per connection, the person its only writer — no `wf` command writes one in this slice, only `wf connections` which lists and validates. Each file: `description`, `server: { command, args, env: string[] }` where `env` holds NAMES only, and `tools: { "<tool>": "read" | "draft" | "send" }`. Refusals: a tool with no class, a class outside the three, an `env` entry that is not a bare name (anything with `=` or a value), a `name` that is not `[a-z][a-z0-9-]*`. Nothing is inferred from a tool's name, ever; the machinery has no list of verbs. THE SECRET, PLAINLY: this slice does NOT improve on today. Workers inherit the daemon's environment (pivot §2.3), so a variable exported for `wf up` reaches every session and every check, not just the server's process. What this slice does add is that a value never enters a file the board reads or the run record freezes, and that `wf start` refuses a run whose connections name a variable that is unset, so the failure is a sentence and not a silent empty header. A per-process secret needs the engine to pass an env map to the spawned server alone — an engine change, named as the next slice's work, not done here. REJECTED: a single `connections.json` (one writer per file — a person editing one connection while a run reads another is the read-modify-write loss the doctrine names); putting connections in the checkout (they are the person's, and a folder run has no checkout); a `secrets:` block of values (a file the api can read is a file the board can leak).

(3) ENFORCEMENT. Recommend: at the filing site the step's task gets (a) `mcp` = exactly the connections the step reaches and nothing else, and (b) `disallowedTools` = the step's `disallow:` plus `mcp__<conn>__<tool>` for every classed tool of every reached connection whose class the step did NOT declare. A deny beats everything whatever the permission mode (measured, `denyingRule` in `apps/api/src/capabilities.ts:—`), the spawn is already `--strict-mcp-config`, and `--tools` is measured not to narrow a server's tools, so the deny list is the fence. CODEX IS REFUSED: `disallow:` is already refused on codex (`disallowOf`), `-c mcp_servers=` has no per-tool deny, so a class could not be kept — `reach:` on a codex step is a load refusal naming claude. REJECTED: an allow-list fence (`permissionMode: dontAsk` plus allow rules) — a `--bg` session in an untrusted directory was measured not to be given that directory's `.claude/settings.json`, so the allow rules may not arrive and the fence would be inert exactly where it matters; a new `allowedTools` field on the engine's task — it would pass the Kubernetes test but it is unmeasured, and this slice should not add an engine field to close a hole the deny list already closes. RESIDUAL HOLE, stated: a tool the connection file does not class is not denied. The file is refused at load if any tool it LISTS is unclassed, but the machinery cannot know a server offers a tool the file omits. Closing it needs an allow-list; it is in `risks` and named as the next slice's measurement.

(4) SEND PASSES A GATE. Recommend (a): the send is its own step, and the step BEFORE it carries `gate: true`. `gate:` holds a step's handoff, so the gated step's successor is never filed until `wf approve` — the send session is never spawned, not asked to behave. The load-time rule, checkable and testable: a step that reaches any `.send` class must have at least one `after:` and at least one of those predecessors must be gated (`after:` is an AND-join, so one gated predecessor is enough). The hermetic proof: run the fixture team to the gate, give no approval, tick again, and the fake mailbox's call log holds no `send` — because no session was started at all. REJECTED: (b) a permission prompt reaching the person — a prompt is a `waitingFor` on a session that is already running with the tool available, the answer arrives through a channel the run record does not own, and nothing in the machinery refuses a send if the prompt is answered wrongly or auto-approved; (c) a `send:` boolean on the step approved by `wf approve` — a second approval mechanism beside `gate:`, with its own bugs, for no gain.

(5) WHAT RUNS. Recommend: FIXTURES ONLY in this slice — `packages/agent-workflows/test/fixtures/mailbox-server.ts` (a fake stdio MCP mailbox with `list`, `read`, `draft`, `send`, appending every call to `$WF_TEST_CALLS`) and two fixture teams under `test/fixtures/teams/`, `mail-digest` (read → note) and `mail-reply` (read → draft → gate → send). Nothing enters `workflows/`. A shipped `mail-digest` would name a connection `mail` that no fresh machine has, so `wf start` would refuse it on every machine but one — the trap the brief names. The shipped teams land in the slice that brings a real mailbox, together with `wf connections add` and a message that says what to create. REJECTED: shipping the two folders now with a README telling a person to write the connection file by hand — it makes `workflows/` dishonest and `apps/api/test/workflows.test.ts` would have to learn about a machine-specific precondition.

(6) THE BOARD. Recommend: the smallest honest picture, folded into what exists — the Capabilities payload grows a `connections` array (name, description, each tool with its class, each env NAME with `set: true|false`, never a value), the existing `/capabilities` route grows a Connections section, and the existing e2e page `240-capabilities.ts` asserts it with one fake connection seeded in `apps/web/test/e2e/seed.ts`. NO new route, NO new page file, NO new line in `pages/NAMES`. The step page already prints a step's keys, so `reach:` shows there for free once `keyValue`/`specOf` know it. REJECTED: a Connections page with a form — writing a connection from the board means the board writes the person's secrets' names into the home store, and a second writer of those files; wait until a person actually needs it. Also rejected: waiting entirely — a fence a person cannot see is a fence they cannot trust.

(7) THE FREEZE, AND CHANGE MID-RUN. Recommend: `wf start` freezes `connections` on the run record beside the workflow folder — for each connection a step reaches: its name, its `server: { command, args, env: [names] }`, and its `tools` with classes. Never a value of anything. The fence a run enforces is then the fence it was started with, exactly as the frozen workflow folder is the steps it was started with. A connection edited or deleted mid-run does not change the run. Env VALUES are read fresh at each filing (level-triggered): if a named variable is unset at filing time, the step is not filed and the run says `connection "mail" needs MAIL_TOKEN in the environment; export it and the next tick files this step` — a wait a person can clear, not a failure. `wf start` refuses up front: an unknown connection name, a class no tool in that connection has, or an unset variable, each with the fix in the message and `exitCode = 2` (the `remoteRefusal` precedent). REJECTED: reading the registry live at each filing — a person editing a connection would silently change a running fence, which is the thing this whole slice exists to prevent; freezing the env VALUES — a secret in the run record, on disk, readable by the api.

## Approach

The slice makes three classes real with one new step key, one new registry file format, and one change at the filing site — and no change to the engine. A node declares `reach: mail.read, mail.draft`. A person's connections live one-file-each under `~/.agent-workflows/connections/`, each naming how to start an MCP server (command, args, env variable NAMES) and classing each of its tools read/draft/send by hand; an unclassed tool is refused at load, never guessed from its name. At `wf start` the run record freezes what each reached connection is (name, server spec, tools-with-classes — never a secret), as it already freezes the workflow folder. At each filing, `runner.ts` gives the engine's task `mcp` = exactly the connections that step reaches, and `disallowedTools` = the step's own `disallow:` plus `mcp__<conn>__<tool>` for every classed tool whose class the step did not declare. A deny rule beats every allow whatever the permission mode, and the spawn is already `--strict-mcp-config`: a session given `mail.read` has no path to `send`. A send is its own step, and the step before it is gated — `gate:` holds a handoff, so without `wf approve` the sending session is never spawned; `validate` refuses at load a step that reaches a `.send` class and does not wait on a gated step. Everything is proved against a fake stdio mailbox in fixtures that records every call it receives; nothing real is connected, nothing ships into `workflows/`.

THREE CORRECTIONS TO THE BRIEF'S ACCOUNT, all checked in the code. (i) The engine's task does carry `mcp`, and both `claude --bg` (`runner.ts`, `claudeMcpArgs`) and the detached runner spawn with `--mcp-config <checkout .mcp.json> <task's file> --strict-mcp-config --no-chrome` — but the task's `mcp` ADDS servers beside the checkout's `.mcp.json` and cannot withhold it. So a step's server set is exact only where the cwd has no `.mcp.json`: that is a folder run (`workspace: folder`, P2's slice, merged). Hence `reach:` is refused on a step that is not `workspace: folder` — not a limitation I like, but the alternative is an engine change to suppress the checkout's file, which this slice should not make. (ii) `agent-workflows` does not pass `mcp` to the engine at all today; the filing site in `runner.ts` sends `tools`, `disallowedTools`, `permissionMode` and the rest, and `mcp` is simply absent. Adding it is a small, local change, not a new seam. (iii) `tools:` is NOT part of an MCP fence: `--tools` was measured not to narrow a server's tools (`features.md`), and `apps/api/src/reach.ts` says so in its header. The fence is the deny list.

WHY THIS SHAPE. The refusals are all at load or at `wf start` — places a test can make refuse with no session, no browser and no money. The one thing prose does here is name the classes; every class is enforced by a rule the harness cannot argue with. The engine passes the Kubernetes test question unasked, because nothing new is needed on the task: `mcp` and `disallowedTools` already exist and already reach the flags.

WHAT THE NEXT SLICE NEEDS FOR A REAL MAILBOX. Four things, none of them in this one: a real server (`@modelcontextprotocol/server-gmail` or equivalent) and the OAuth dance that produces a refresh token; a secret store — today a worker inherits the daemon's whole environment, so a per-connection secret needs the engine to pass an env map to the spawned server's process alone, which IS a new field on the task and does pass the Kubernetes test (`envFrom`); `wf connections add`, which writes a connection file and tells a person what to export; and the two shipped teams, `mail-digest` and `mail-reply`, with the folder-run trust prompt fixed (run `7a87`) so they start on a fresh machine.

## Risks

- THE UNLISTED TOOL. The deny list covers the tools a connection file classes. A server that offers a tool the file omits is not denied, and no test can catch it, because the machinery never asks the server what it has. This is the honest limit of a deny-list fence. Closing it needs an allow-list — `--allowedTools` plus `dontAsk` — which is unmeasured and whose settings were measured not to reach a `--bg` session in an untrusted directory. Named as the next slice's measurement, not hidden.
- THE CHECKOUT'S `.mcp.json` RIDES ALONG. `claudeMcpArgs` passes both files, so a step's server set is exact only where the cwd has none — a folder run. Tying `reach:` to `workspace: folder` is a real restriction, and if the owner wants mail nodes in a repository run the engine must learn to suppress the checkout's file. Not in this slice.
- THE SECRET STILL REACHES EVERYTHING. Workers inherit the daemon's environment, so a token exported for `wf up` is visible to every session and every check, including a step that reaches nothing. This slice does not fix that and does not pretend to; it only keeps values out of files. A real mailbox should not be connected before the per-process env field exists.
- A FOLDER RUN STILL BLOCKS ON THE TRUST PROMPT. The live finding from run `7a87`: a `--bg` session in a plain folder waits on Claude Code's workspace-trust prompt. The hermetic tests use a fake engine and do not care, but the AE_LIVE test and any real mail team do — so the live measurement may block until that fix lands.
- THE GATE RULE IS STRUCTURAL, NOT SEMANTIC. It proves a sending step waits on a gated step; it does not prove the gated step is the one whose output is sent, nor that a person read the draft before approving. A team wired to gate something irrelevant would pass. The check that would catch it is `input:`/`output:` wiring, which is P4's ground.
- PARALLEL RUNS. Another run is changing the inbox and the board's start form; `apps/web/src/lib/api.ts`, the builder mirror and CLAUDE.md are shared surfaces. Merge main before implementing and again before signing off, and read a union-merged CLAUDE.md rather than trusting the merge.
- THE WEB SURFACE IS THE THINNEST PART OF THIS PLAN. I could not run `npm run build` or `npm run e2e` in this step, so the Connections section is planned from the route's shape and not from a picture. If it wants a page of its own after all, that is a new file under `pages/` AND a line in `pages/NAMES`.
