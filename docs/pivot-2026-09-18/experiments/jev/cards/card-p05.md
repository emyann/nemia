Every run of an agent ends in an outcome: a task that asked for a closing statement never succeeds without one, and one nudge is tried before a person is asked — agent-engine and agent-workflows

This is P0.5 of docs/pivot-2026-09-18.md (§6), shaped by the owner on 2026-09-19: "an agent run should always finish with an output, even if it is to say nothing … making sure that an agent always has an outcome is how we will make sure that the system is stable and that people can understand what they are building." Read §3 of that document for the model it serves: a workflow is a graph of nodes, what is attached to a node does the work, and typed data flows between nodes — so what a node's run ENDS with must be a record of one known shape, whoever or whatever ran.

Measured 2026-09-19 over ~/.agent-workflows/engine/tasks: 351 agent tasks, 342 filed with a `closeoutSchema` (agent-workflows always asks: `closeoutSchemaOf` returns `CLOSEOUT_SCHEMA` at the least), 6 ended with no statement — and the engine journalled 5 of those 6 as `observed: done, reason: harness`, settled `succeeded`. The cause is in `decide` (packages/agent-engine/src/domain.ts, the branch for an attempt in flight with a sighting): `unsigned` is `quiet && closeoutSchema !== undefined && closeout === undefined`, so a session whose registry says `done` — not quiet — with no statement is recorded as a success. open-issues.md predicted this "second door" and had not measured it. agent-workflows catches it a layer up (run.ts: "a task that settled `succeeded` with nothing said is `unsigned` too") and the step waits on a person. Every time, a person's `wf retry --message "you ended without calling StructuredOutput … sign off now"` closed it in 25–43 seconds for $0.66–$0.93. The engine's own nudge (`NUDGE` in domain.ts, given to a resumed attempt after an `unsigned` end) has never once run: no shipped step sets `retries:` and every task is filed `maxAttempts: 1`.

1. THE ENGINE'S RULE. A task filed with a `closeoutSchema` never settles `succeeded` without a closing statement, by any path its session ends: quiet, or the harness saying `done`. Such an end is `unsigned`, recorded `failed`, exactly as the quiet path is today. One condition in `decide`, not a branch in engine.ts. A task filed with no schema is unchanged: the harness's word, or quiet, is the only end it has. Tests: the `done`-without-a-statement sighting, which fails without the change; an old journal that recorded such an end still folds as it did.

2. ONE NUDGE BEFORE A PERSON. When an attempt ends `unsigned`, the same session is continued once and told what the owner's hand nudges told it — it ended without calling StructuredOutput, the work stands, change nothing, sign off now; if the work is not finished, finish it and then sign off; if it cannot be finished, sign off anyway saying what stops it. Decide WHERE this lives and say why: in the engine (an allowance beside `maxAttempts`, so a task filed `maxAttempts: 1` may still be nudged once — mind that `maxAttempts: 2` would also restart a session clean after a harness verdict, which nobody wants here), or in the run (agent-workflows files one `--nudge` try on its own when a try ends `unsigned`, as `wf retry --nudge` does on a person's word, recorded as a try with its cost). Whichever you choose: it happens once per step per round, never in a loop; it is filed with the same schema, model, effort, context window, tools and permission mode as the session it continues (the session-cache test pins that — join it); a nudge that also ends unsigned leaves the step `unsigned`, waiting on a person, as today; and `wf ls`, `wf decide` and the board's existing words say that a nudge was tried.

3. AN OUTCOME OF ONE SHAPE, AND WHO WROTE IT. Write down, in the engine's README and in features.md, the contract this establishes, and make the records keep it: every ended attempt carries either the AGENT's statement (its typed payload, untouched) or the MACHINE's reason there is none (`lost`, `stopped`, `budget`, deadline, `unsigned`) — never neither, and never words the machine wrote in the agent's name. If any end today leaves neither on the record, close it and test it. Do not invent a new envelope type unless the existing `ended` event cannot say it; say in your closeout, in a few lines, what a later "every kind of node ends in the same outcome record" (a check's exit code, a script's JSON, an agent's statement) would still need — the owner wants to render a node's outcome from its schema on the board, and that is a later card.
