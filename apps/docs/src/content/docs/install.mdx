---
title: Install
description: Install a released Nemia on a Linux or macOS machine with one command, as a server or as a client of one, and keep it up to date.
---

A released Nemia is one archive per platform: Linux on x64 or arm64, and macOS on Apple silicon. It carries its own Node, the code,
the production dependencies with that platform's Claude Code, the board's built pages and the templates. Nothing else is installed
system-wide, and no root is needed. A dedicated machine, such as a small VPS running Ubuntu 24.04, is the first place it is made for.

## Install

```bash
curl -fsSL https://github.com/emyann/nemia/releases/latest/download/install.sh | sh
```

The installer checks the machine first: it needs git, tar, curl or wget, and sha256sum or shasum. On Linux it also looks for
systemd's user manager and cgroup v2, which the service and per-session memory limits need, and warns where one is missing rather than
stopping. Then it downloads the archive for this machine and the release's checksums, refuses an archive whose checksum differs, and
lays the release down:

- the release folder in `~/.agent-workflows/releases/<tag>` (the store, `WF_ROOT` where you set it), unpacked beside it and renamed
  into place, so it is there whole or not at all;
- the release's pointer, the link `current` beside it, moved to it;
- the command, `~/.local/bin/nemia`, a link to the release's own launcher. Put `~/.local/bin` on your PATH if the installer says it is
  not.

Then it asks three things, on the server, each of which you can also answer by a flag with `--yes`, for a machine you set up by
script:

- **Your Claude token** (below), asked outright and read without echo, which it hands to `nemia claude-token set` on its standard
  input. With `--yes`, pass it as a file: `--claude-token-file <file>`; without one, it warns and goes on.
- **Starting at login.** Yes runs `nemia service install --size auto`: a systemd user unit on Linux, or a launchd agent on macOS,
  with as many concurrent sessions and as much memory each as the machine's size allows. On Linux it also runs
  `loginctl enable-linger`, so Nemia keeps running after you log out. `--no-service` skips it; `nemia up` runs the daemon by hand.
- **The address to bind** (below), picked by number from this machine's private addresses (`nemia service addresses` lists them with
  their kind), or typed. Left at its default, the daemon listens on this machine alone.

Other flags: `--version <tag>` installs that release instead of the latest, `--base <url>` downloads from another place laid out
as GitHub lays out a release, and `--board-base <url>` is the address the first-visit link is printed under (below).

The installer prints no token. It ends on `nemia readiness` (below): what is in place, and the command that fixes each piece that is
not.

## Bind it to a private network

By default the daemon listens on 127.0.0.1, and the board and the api are for this machine only. To use them from your laptop, bind
the daemon to an address of a private network you trust, such as your Tailscale address:

```bash
curl -fsSL https://github.com/emyann/nemia/releases/latest/download/install.sh | sh -s -- --bind 100.64.0.1
```

or pick that address at the installer's question. A public address, or every interface (`0.0.0.0`), is refused unless you acknowledge
it with `--public`, which writes `NEMIA_BIND_PUBLIC=1` into the service: the daemon refuses to start on such an address without it.

A store bound beyond this machine is marked exposed: every caller then needs a person token, the board included, and the server's own
`nemia` too. The installer mints the server's own token straight into its local context, never printed, so `nemia ls` and the other
verbs work there as before. In place of a token, it prints a first-visit link: open it within ten minutes and that browser is signed
in to the board, once. `nemia board link` makes another (`--base <url>` prints it under the name your browser uses, a Tailscale name
or a proxy's, since a browser keeps one cookie per host name). Where you bound the daemon by hand, keep a token for the server's own
`nemia` in a file:

```bash
nemia token add server
nemia config set-context local --token-file ~/.nemia-token
```

The board signs in by a first-visit link, by pairing (_Pair this browser_ on its sign-in shows a code you approve at the server), or by
a pasted token, and keeps it in a cookie only the board's own origin is sent.

Nemia speaks plain HTTP. TLS stays outside it: a private network such as Tailscale, which encrypts the traffic between your machines,
or a reverse proxy of your own in front of it.

## A client of another machine

On your laptop, Nemia can be just the command that talks to the daemon of your server:

```bash
curl -fsSL https://github.com/emyann/nemia/releases/latest/download/install.sh | sh -s -- --client --server http://100.64.0.1:8787
```

A client install starts no service. It pairs with the server: `nemia pair <url>` shows a short code, you approve it on the server
(`nemia pairings approve <code>`, or the board's Setup page), and a person token named for your laptop lands in a context, a name for
that server in `~/.config/nemia/config.yaml` (readable by you alone), made the current one. No token is shown or copied; `nemia token
rm <name>` on the server revokes it. `--token-file <file>` still takes a token you minted by hand. A context is the same idea as
kubectl's:

```bash
nemia config set-context vps --server http://100.64.0.1:8787 --token-file ~/.nemia-token
nemia config use-context vps
nemia config get-contexts
nemia config current-context
```

Setting `NEMIA_CONTEXT=<name>` picks another context for one command. Under a remote context, the reads and the client verbs (runs,
proposals, the inbox, decisions) reach the server, and so does every other verb about the store: `nemia` parses it, checks it and
prints its answer on your laptop as it always does, and the server does the work. The files a command names on your laptop, a card
for `nemia inbox add -f`, a template folder or archive for `nemia factory apply --template`, a file for `nemia factory resolve
--file`, travel with the request. A repository path (`--repo`) or a volume's path names a folder on the server's machine, not on
yours. A verb no endpoint of the server serves yet is refused, naming the context to leave (`NEMIA_CONTEXT=local`) or the machine to
run it on.

The machine's own verbs always act on the machine you type them on: the service, upgrade, the daemon (`nemia up`, `nemia tick`), the
version, tokens and the Claude token, and the verbs that read and write files and no store (`nemia template`, `nemia frontmatter`,
`nemia admit`). `nemia template export --factory` reads a factory of this machine's store, so under a remote context it is refused:
run it on the server.

Claude Code's nemia plugin asks the server through the current context's token (`nemia config headers`, its `headersHelper`), at the
address `NEMIA_URL` names: `nemia pair` prints the line to put in your shell profile.

## What is in place

```bash
nemia readiness
nemia readiness fix <need>
```

One read lists every piece a server needs before a factory's first run, each in place, missing or unknown, with the command or fix
that puts it there: the Claude token (set and loading; a wrong or expired token shows only when a session is refused), the service and
its linger, the bind, cgroup v2 and `systemd --user`, the git identity, the needs each factory's workflows declare, a factory, and a
newer release. On a laptop it adds whether its context reaches the server and its token is taken. The board's Setup page shows the
same read, and a banner on every page while a piece is missing.

A workflow declares the machine needs it has, and a fix for each: sdlc's `build` and `quick`, where the factory lands on GitHub, need
the GitHub CLI signed in with the `workflow` scope. A run of such a workflow waits before its first session while a need is missing,
naming it and its fix, and starts by itself once the need is met. `nemia readiness fix <need>` (or its button on Setup) runs the fix on
the server and shows its output as it runs, a sign-in's device code set apart: open the link it shows on any device and type the
code. A fix installs a tool into `~/.agent-workflows/tools`, never as root, and the daemon puts its `bin` first on its PATH. A
factory's fix runs only once you trusted its places (`nemia factory trust <factory>`).

## Your Claude token

The sessions run Claude Code on your Claude subscription. On a server with no browser, make a long-lived token on any machine where
you are signed in, and give it to the server:

```bash
claude setup-token
nemia claude-token set
```

`claude setup-token` opens the browser sign-in and prints a token valid for a year; paste it into `nemia claude-token set`, which reads
it from standard input. The token is kept in `~/.agent-workflows/claude-token`, readable by you alone, and the daemon loads it when it
starts, however it was started. `nemia claude-token status` says whether one is set, never the token itself, and
`nemia claude-token rm` takes it away. Nemia never sends, logs or serves it, and the board never asks for it.

Each person uses their own token, on their own machine. A server that others use while it runs on one person's token makes that
person's account available to them, which Anthropic's
[Consumer Terms of Service](https://www.anthropic.com/legal/consumer-terms), section 2, _Account creation and access_, forbid: "You also
may not make your Account available to anyone else."

A token made by `claude setup-token` can only make model requests: it cannot open Remote Control sessions or reach claude.ai's
connectors. Sessions on a server signed in this way run without Remote Control, and say so; the MCP servers a factory configures
itself still work.

## A repository by its URL

A factory may name a repository by its git URL rather than a folder of the machine:

```bash
nemia factory add mill --repo git@github.com:you/mill.git
```

Nemia clones it under `~/.agent-workflows/clones/<host>/<path>` before it files the factory, and the daemon clones it again if that
folder goes. The clone uses the machine's own git credentials, and Nemia holds none: for an SSH URL, an SSH key the host accepts, with
the host's key in `~/.ssh/known_hosts`; for an HTTPS URL, a git credential helper for the host. On GitHub, `gh auth login` sets one up.
A URL that carries a password is refused. A clone that fails is refused with git's own words and the setup to do, and nothing is filed.

## Signing Codex in

A Codex step does not start while Codex is signed out on the machine; its refusal says so. On a server with no browser, sign in with a
code you enter on any device, as the user the daemon runs as, then try the step again:

```bash
codex login --device-auth
codex login status
```

## Upgrade, and going back

```bash
nemia upgrade
nemia upgrade v1.3.0
```

`nemia upgrade` installs the latest release, or the one you name, beside the current one, checks it starts, and moves the pointer to
it. Moving forward, the store is read as it is and never rewritten. Going back is refused past the oldest release that can read the
store as it now is, and the refusal names that release.

`nemia version` says the release you run and, when there is one, the newer release. The board says it too. To know that, the daemon
of an installed release reads the release list's newest entry every six hours, sending nothing about you or your store. Set
`NEMIA_RELEASE_CHECK=off` in its environment to turn that off; a checkout of the repository never checks.

## Signing in from a remote browser

Some sign-ins open a page in a browser that then calls back an address on the machine that asked, such as a factory's MCP server
signing in. On a server, that address is the server's own 127.0.0.1, which your laptop's browser cannot reach.

A factory's MCP server signs in from your own browser wherever the daemon runs. Press _Sign in_ on the server's row of the board,
open the page it gives and approve. Your browser is then sent back to an address like
`http://localhost:8791/callback?code=…&state=…`, which does not load, since nothing listens for it on your laptop. Copy that address
from the browser's address bar, paste it into the field the board shows under the waiting sign-in, _the address your browser landed
on_, and press _Complete_. The daemon hands it to the sign-in waiting for it, and the server reads `connected`. The address carries a
code used once: Nemia never logs or keeps it.

Or, instead, forward the port over SSH and open the page on your laptop, so the call back reaches the server itself:

```bash
ssh -L 8787:127.0.0.1:8787 you@your-server
```

Put the port the sign-in's address names in place of 8787 when it is another. With the tunnel open, the page's call back reaches the
server.

Signing in to Codex on a server, and a factory naming its repositories by URL to be cloned, come in a later release.
