---
title: Factories
description: A factory names the repositories a body of work is on, the workflows it offers, the agents it hires into their steps, its rules and its instruction.
---

A factory is a body of work, named. It says which repositories the work is on, which workflows it offers, which agent does each step,
what every agent at work in it is told, and what Nemia is to know about it. Every run is started in a factory.

**It owns** its repositories, the workflows attached to it, its hires, its rules and its instruction.

**It never touches** a run already started. A run reads its factory once, when it starts, and freezes what it read: a hire or a detach
afterwards reaches only the runs started after it.

**It is reached through** one file in your store, `~/.agent-workflows/factories/<name>.json` (`WF_ROOT`), written by the `nemia factory`
verbs and by the board. Its name is the file's. The code is in `packages/agent-orchestrator/src/factory/`.

```bash
nemia factory add pipao --repo ~/code/pipao          # a factory on one repository
nemia factory attach pipao build                      # it offers the workflow build
nemia factory hire pipao ada --step build/implement   # ada does build's implement step
nemia start "add a flag" --workflows build --factory pipao
```

A factory can be made from a template too, its workflows, agents and hires given at once: Nemia has one built in,
[sdlc](/sdlc/), the team that builds Nemia, which `nemia factory apply` finds by its name.

## Its repositories

A factory names one repository or more, as folders on your machine (`"repos"` in its file). A run works in one of them, in a worktree
of its own. Every other repository of the factory is mounted for each step read-only (`factoryMounts`), so a step can read the code it
does not change. A step that must write one of them says so with `writable`, naming the folder; that widens where its writes reach,
never what it may do.

When you add a repository or a plain folder to a factory (`nemia factory add`, `nemia factory apply`), Nemia trusts it for the harness
its steps run on, at that moment: for Claude Code, the folder's entry in Claude Code's own configuration file, on the repository's root. Without that
trust the harness drops the allow rules of the folder's own project settings, and a step is refused commands the repository
meant to allow. The command prints the place, what the trust grants and how to take it back; `--no-trust` adds the place without it.
A place that is not trusted — added before, opted out, or taken back — is said by `nemia factory` and on the factory's page, with the
line that trusts it: `nemia factory trust <name>`. A run's denied calls on such a place name it as the likely cause.

## Its volumes

A factory can name volumes too: folders on your machine its steps may reach beyond the run's workspace, apart from the repositories it
works on, as a container is given a volume. Each is marked as docker compose marks one, read-only or writable, and the mark is required:
a volume left unmarked would be writable without anyone having said so, and Nemia's runtime refuses an unmarked mount for that reason.

```sh
nemia factory volume add pipao /home/me/notes:ro    # every local step reads it
nemia factory volume add pipao /home/me/scratch:rw  # a step whose fence writes may write it
nemia factory volume rm pipao /home/me/scratch
```

- Every local step of a run in the factory is given the volumes, beside the read-only mounts of its other repositories. A writable
  volume is writable only for a step whose fence writes; a step that writes nothing reads it.
- **A writable volume is not the run's workspace.** Nothing commits, lands or reverts what a step writes there, and every run of the
  factory reaches it at once.
- A volume never makes the factory work on its folder: which factory a start, a card or a schedule lands in does not change.
- A run copies the volumes at its start, so a later change reaches only the runs started after it.
- Refused: a folder that is no directory, one of the factory's repositories, a writable folder inside one of them or holding one
  (a step would write the repository outside its worktree), a folder at or inside Nemia's store, and a writable one that holds the
  store. A start is refused, before anything is written, where a step's harness cannot hold a volume's mount: Codex holds
  no writable one.
- Volumes are yours: they live in the factory's own file (`"volumes"`, each `{ "path", "readOnly" }`), never in a template, and
  `nemia factory adopt` and `nemia factory upgrade` keep them. `nemia factory` lists them under the factory, and the board on the
  factory's settings page, each with its mark and the line that takes it back; the board writes none.

## Its harness settings

A factory can name settings of a harness that every session of its runs' steps on that harness is given, on top of the repository's
own settings, as a container is given its configuration by its Pod. Say a preference once, and every repository the factory works on
has it: no file is written into a repository, and for Claude Code the settings reach the session through the Agent SDK's settings
option. The value is JSON:

```sh
nemia factory setting set pipao claude.attribution '{"commit":"","pr":""}'  # no Co-Authored-By trailer, no pull request line
nemia factory setting rm pipao claude.attribution
```

- A factory sets `claude.attribution`, `claude.includeGitInstructions` and `claude.language` alone. Each changes what a session writes
  or says, and none what it may reach or run.
- Every other key is refused, naming where it is owned instead: permissions are a step's `allowedTools:` and `disallowedTools:`, hooks
  the repository's `.claude/settings.json`, MCP servers an agent's `mcp:` and `nemia factory server add`, and a key that runs a program
  (`apiKeyHelper`, `statusLine`, …) is no factory's. Claude Code's settings keep growing, so the list says what is allowed: a new key is
  a decision someone makes, never one let through unjudged.
- A step's own agent's settings win a key both name. A step on Codex, or on a remote agent, is given none.
- A run copies the settings at its start, so a later change reaches only the runs started after it. A key a factory may not set,
  written into its file by hand, refuses every start in the factory until it is removed.
- Settings are yours: they live in the factory's own file (`"harnessSettings": { "claude": { … } }`), never in a template, and
  `nemia factory adopt` and `nemia factory upgrade` keep them. `nemia factory` lists them under the factory; the board shows none yet.
- The default factory holds none, as it holds no volume: a run that names no factory is given no factory setting.

## Attached workflows

A factory offers only the workflows attached to it, and none until one is. Attaching records the workflow's folder name in the
factory's file (`"workflows"`); detaching takes it back. Starting a workflow a factory has not attached is refused, naming the attach that
would add it (`unattachedRefusal`).

## Hires

A step need not name its agent: a factory hires one into it. A hire maps a step, written `<workflow>/<step>`, to an agent
(`"hires": { "build/implement": "ada" }` in the file). So two factories can run the same workflow with different agents.

- A step whose own file names its agent is filled already, in every factory, and takes no hire.
- When a run starts, each hired step is read exactly as if its file named the agent, and frozen so on the run.
- A start that would leave a step with no agent is refused, naming each such step and the hire that would fill it (`unfilledRefusal`).

## The default factory

Runs and cards written before every run had a factory are in the default factory. It is no file: it holds that history, offers every
workflow, hires no one, and starts nothing. A start that names it is refused (`defaultStartRefusal`). A start that names no factory
runs in the one whose repository it is typed in.

## Its rules

A factory has rules of its own: its rules and policies, in markdown, told to every agent hired into it. They are one file, kept in your
store with the factory and never in a repository, `~/.agent-workflows/factories/<name>/RULES.md` (`WF_ROOT`); a factory made from a
template keeps it in its tree, where a template carries it and an upgrade merges it as text.

- `nemia factory rules <name> --file <path>` writes them, `nemia factory rules <name>` prints them, and `--clear` removes them. The
  board's page of the factory's settings reads, writes and clears them too.
- Every step of every run started in the factory is told them, after the agent's custom instructions and before the step's own policy:
  the fourth of an agent's [instruction layers](/agents/#what-an-agent-is-told-five-layers), which the step's own policy outranks. A
  step on a remote agent is told none.
- A run reads them when it starts and keeps them (`StepAgent.factoryRules`), as it keeps every revision it resolved: an edit reaches the
  runs started after it, and a run in flight only where the factory follows revisions or a person refreshes it ([its
  revisions](#its-revisions)).
- They only add words. A frontmatter block is refused (`factoryRulesRefusal`): they set no key, give no tool and widen no fence.
- A factory with none tells nothing, and the default factory keeps none.

## Its instruction

A factory has one instruction: what Nemia is to know about this body of work, in markdown. By default it is `NEMIA.md` at the root of
the factory's first repository, edited with the code it speaks of. The factory's file may point at another file of that repository,
or keep the words in your store instead, for a repository you would rather not write into.

- [Nemia](/nemia/) reads it before she acts in the factory.
- The board shows it on the factory's settings page, and the api serves it (`packages/agent-orchestrator/src/factory/instruction.store.ts`).
- It is not told to a step. What every agent hired into the factory must know belongs in [its rules](#its-rules), and what holds in
  one repository in the files the harness reads there, `CLAUDE.md` or `AGENTS.md`: the fourth and the third of an agent's
  [instruction layers](/agents/#what-an-agent-is-told-five-layers).

## Its revisions

A run keeps the workflow, agents, skills and rules it resolved: a fix merged while it runs does not reach it by itself. A factory says
whether it should, with one key, `revisions`, in its file, as a Pod's `imagePullPolicy` says whether a container takes a newer image:

- `pinned`, the default, as `IfNotPresent`: a run keeps what it resolved at its first filing until a person refreshes it, with
  `nemia refresh <run>`.
- `follow`, as `Always`: every new filing of a run, a step, a retry or a round, is filed on the revisions the files hold then, as
  `nemia refresh` would take them. What was already filed is not run again, and the run's steps are neither added nor removed.
  `nemia refresh` is refused of such a run, since there is nothing to ask for.

A run that has filed nothing takes the files afresh at its first filing either way.

- `nemia factory revisions <name> follow` (or `pinned`) writes it, and `nemia factory ls` prints it under the factory.
- A factory made from a template says it in its manifest, as `spec.revisions`, which the render writes into its tree's wiring;
  `nemia factory revisions` writes the wiring after.
- Every pass of the daemon reads it, so a run in flight takes a change of it at its next filing.

## Change a template's parameter

A factory made from a template keeps the parameters it was applied with in its file (`template.params`). To change one without a new
version of the template, preview it at the version the factory is applied at, then type the line the preview prints last:

```bash
nemia factory diff pipao --to 2.5.0 --set ciCheck=build          # 2.5.0, the version applied
nemia factory upgrade pipao --to 2.5.0 --set ciCheck=build --plan sha256:…
```

The preview merges three ways, as an upgrade does: the base is the template at that version rendered with the parameters the factory
was applied with, ours is its tree, and theirs is the template rendered with the new ones. The upgrade writes the parameters into the
factory's file, held to the plan you previewed, and the daemon merges on its next pass, waiting on `nemia factory resolve` where your
tree changed the same line. A parameter changed in the file by hand is merged the same way. A template whose files changed under the
version the factory was applied at is still refused: give it a new version, and upgrade to that.
