# The pivot: from a coding board to a machine for agent teams

Written 2026-09-18, from one long working session between the owner and Claude. It records what was
measured that day, what was argued, what the owner decided the project is for, and the work that
follows from it, in order. Nothing in the repository's code changed that day. Every number below was
measured on this machine's own records unless it says otherwise.

**The decision in one paragraph.** The project stops being "the harness kanban board" for writing
code. It becomes a machine a person can trust with work of any kind: things go into an inbox, the
machine works out what each thing is and which team of agents should do it, the agents do bounded
jobs and sign typed results, and anything that reaches the outside world waits for the person. Code
is one kind of work among others. It ships as open source that runs on a person's own machine, and
as a hosted product for people who want to sign in, pick a preset (a Getting Things Done preset
first) and put things in their inbox. The building block is the **agent**, not the step.

Contents: 1 what the day measured about cost · 2 what it learned about Jev · 3 the vision ·
4 the code against the vision · 5 what stays · 6 the work, in order · 7 the name · 8 open decisions ·
9 corrections made along the way · 10 where the evidence is.

## 1. Cost: where the subscription goes

The day began with a worry: the Claude subscription drains fast, and perhaps a resumed worker pays
for its context twice. Measured over 234 worker sessions, 9,394 model calls, 12–18 September.

**The totals.** About $2,168 at API prices. Claude Code's own recorded costs fit these rates to within
1%: cache write $10 per million tokens (every write is the one-hour kind), cache read $0.50, output
$25, and no surcharge past 200k tokens of context.

| Token class | Cost | Share |
|---|---|---|
| Cache reads | $1,050 | 48% |
| Cache writes | $671 | 31% |
| Output | $446 | 21% |
| Uncached input | ~$0 | 104k tokens in all |

Caching works: 96.9% of input tokens are cache reads. The spend is the *volume* read.

**Finding 1 — context is never compacted.** Workers get the one-million-token window and not one of
234 sessions ever compacted. The median session peaks at 173k tokens, the 90th percentile at 441k,
the largest at 831k. Three quarters of all input tokens were spent in calls carrying more than 200k.
What enters a session is small (about 16M tokens of tool results in all); each token is then re-read
about 130 times. A cap at 200k would save at most 17%, at 150k about 22%. The knob exists:
`claude --autocompact <100k–1M>` and `CLAUDE_CODE_AUTO_COMPACT_WINDOW`, both present in the 2.1.277
binary. A later measurement added: a first session reads a median 82k tokens of tool output before
its first edit, which is 9% of all spend.

**Finding 2 — a resume is cheap unless the closeout schema changes.** All 29 resumes with an
unchanged schema reused the cache. All 43 resumes whose schema had changed rewrote the whole
conversation, 200k–640k tokens each at twenty times the read price: 14.1M tokens, about $134. The
cause is `closeoutSchemaOf(step, owesReplies(…))` at `packages/agent-workflows/src/run.ts:2613`,
which adds `replies` from round 2. That changes the `StructuredOutput` tool, which sits at the front
of the cached prompt. Even warm, a resumed round is dear because it starts at 450k tokens: $0.41 per
call against $0.23 for a first attempt and $0.14 for a review, which starts fresh. Implement rounds
and `respond` are 31% of spend.

**Finding 3 — workers very likely run at the owner's global `xhigh` effort.**
`~/.claude/settings.json` sets `effortLevel: xhigh`; no step sets `effort:`. Not proven from the
transcripts; output averages 1,900 tokens per call.

**Finding 4 — parallel workers compress spend, they do not add to it.** The daemon's ceiling is four
sessions. The peak five-hour window was $384; 17 September alone was $888.

**Finding 5 — the owner's own sessions are about 29% of all tokens read.** Twelve sessions in the main
checkout ran at a median 511k tokens of context per call.

**Visibility.** The board already shows dollars per attempt. Missing: `transcriptUsage`
(`packages/agent-engine/src/runner.ts:535`) adds three input classes into one `inputTokens` though
their prices differ twenty-fold, which is what hid Finding 2; peak context per attempt is not
recorded; and the quota itself is readable — the JSON Claude Code hands a statusline script carries
`rate_limits.five_hour` and `seven_day` with `used_percentage` and `resets_at`. How the subscription
weighs cache reads is not documented; logging `used_percentage` against the token classes for a day
would settle it.

## 2. Jev: what a typed judgment can and cannot do here

Jev (`jev-1.13.0`) is TypeSafe's "System One" model. It takes a `state` and typed questions and
returns a Choice (one of a closed set), a Noul (the probability of yes) or a Score (a place on
described levels), with probabilities. It writes no text. 32k tokens of state per request; $0.042
per million input tokens, output free. The key is `TYPESAFE_API_KEY` in the repository's git-ignored
`.env`. The SDK is `@typesafe-ai/sdk` 0.6.0, with no runtime dependencies; it was only ever
installed in a scratch directory.

### 2.1 Measured on this machine

- **Latency:** 181 ms at 434 tokens, 309 ms at 9k, 616 ms at 31k. Seventy-seven questions in one
  request (about 25k tokens) took about 420 ms.
- **Billing:** the state is billed once per request, not once per question.
- **Not deterministic, but consistent.** Over three identical askings of 1,155 pairs, none crossed
  0.5 or 0.8 and one crossed 0.9. Vaguer questions are worse: 1.7–2.5% crossed 0.5 in the context
  track. An answer must be asked once and recorded.
- **Irrelevant state inflates confidence.** The same ambiguous question went from 0.67 to 0.99 when
  8k tokens of unrelated, reassuring filler joined the state. A threshold holds for one shape of
  filtered state only.

### 2.2 Round one, and why it was wrong to trust it

Nine agents surveyed four layers for places Jev could *replace* something, and rejected 11 of 12.
That verdict was shaped by its brief. No agent read a TypeSafe page or made a call; the briefing they
were given was half caveats; each skeptic was told to refute; and the question was the wrong one for
this codebase. It was built when the only judges were an agent session at $5–10 or the owner, so
every design decision had already moved judgment *out* of the machinery — into exit codes, files,
schemas, a step, a gate. A survey of existing code finds nothing to replace because those sites were
designed away. Two of its assumptions then failed against measurement: Jev read "a seventh finding…
leave it" correctly (0.05), and its answers were stable.

The probe that followed: *does this brief ask for this review finding to be fixed?* Fifteen briefs
against 77 open findings, 22 hand-labelled positives. At 0.8, precision 1.00 and recall 0.86; at 0.5,
0.92 and 1.00. Plain code (shared backticked symbols and the file named) at the same recall:
precision 0.15. Jev also corrected the labels — its two confident "false positives" were a sixth
leftovers brief nobody had identified. A full pass over 76 briefs found 32 findings taken up, 5
unsure, and 40 no later brief asks for (an upper bound: a hand commit or a plan note is also a fate).

### 2.3 Round two: design work, with the skill, the docs and live calls

Four designers loaded the `typesafe:typesafe-ai` skill, read 14–17 documentation pages each, and made
about 3,000 live calls for about $0.32. Two skeptics re-ran every scoring script; every number
reproduced.

| Track | What it measured | Skeptics |
|---|---|---|
| The workflow language | brief → "touches `apps/web`" 71 of 71; the owner's own folder pick was wrong on 3 of 71 | probe more / build |
| The supervisor | a reviewer's prose → "another round?": 89 of 113 decided, all right, 24 unsure | probe more / probe more |
| Context selection | brief → packages P 1.00 R 0.88; `CLAUDE.md` traps P 0.57 | drop / drop |
| Effect + Jev | recorded layer: second run made 0 network calls; replay answered 1,155 judgments with no key | probe more / probe more |

**The general finding: Jev reads a judgment someone stated; it cannot make one.** It works when the
answer is in the text it reads. It fails when the answer needs context nobody wrote down: deciding
from the findings alone whether another round is worth it scored 0.70 against 0.71 for "the list is
not empty", with 26 confident wrong answers.

**Hostile text.** A sentence added inside the judged text moved 25 of 54 answers. With a code-written
fact beside the text (a check's exit code), between 0 and 3 of 33 moved. Text steers Jev when it is
the only evidence. So a fence belongs on what *evidence* a question may read, not on field names.

**Where the skeptics deflated it.** The best-scoring questions are ones code knows exactly by the
time they matter (the diff after implement; the exit code; the reviewer's `again` field). A plain
`'apps/web' in brief` reaches precision 0.94, so Jev's margin there is 0 errors against 5, not
against 27. Seventy percent of "suggested files" were already named in the brief. One author, one
week, nothing held out.

**Effect + Jev.** The owner's hunch holds inside one package behind a plain Promise interface, which
is how the engine already uses Effect (`facade.ts`: "Effect is how this engine is written, not how
it is used"; `agent-workflows` imports none, on purpose). A `Judge` service, live / recorded / replay
layers and typed errors earned their place. `Schedule` retries did not: the SDK already retries.
Prototype bugs to fix before reuse: a recorded failure withholds the recorded answers beside it, and
an answer is decoded before it is saved.

**Architecture facts the designers missed.** `start()` has four callers, one of them the tick's own
`startQueued` (`runner.ts:2185`), so "ask at `wf start`" puts a network call in the tick. Only a task
filed from the pass, as a check is, fits every path. And workers inherit the daemon's environment, so
a key set for `wf up` reaches every session and every check.

**Plain-code findings that outweigh any Jev feature.** Three of 71 runs changed `apps/web/src` on a
folder with no build or e2e check. The owner clicked the recommended option 85 of 88 times. Most of a
supervisor's pass is arithmetic over records. An engine defect: a session the registry calls `done`,
with a closeout schema and no closeout, settles `succeeded` (`agent-engine/src/domain.ts:490-496`),
and every task is filed `maxAttempts: 1`, so the nudge has never run (0 `unsigned` ends in 453
journals).

### 2.4 The dispatcher, tried live

The owner's example card — "a new home item in the menu and a homepage surfacing the most important
thing a user should know" — and five others, against the real workflow folders, each asked twice,
$0.00017 a request.

| Card | One question: which workflow? | The same request, as properties |
|---|---|---|
| The home page | `ui` 0.79 | seen on a page 0.93 · front-end source 0.89 · **plan first 0.84** · clarity 1.35 of 3 |
| A typo in the engine's README | `dev` 0.83 | plan first 0.07 |
| The engine records token classes | **none of these 0.54**, `dev` 0.39 | plan first 0.77 |
| "Make it faster." | none of these 0.74 | clarity 0.92 of 3 |
| sqlite across three packages | 0.42 / 0.40, and it **flipped** on the second asking | plan first 0.86 |
| "Watch my runs, tell me on my phone" | `supervisor` 0.98 | — |

Four lessons. **Ask for properties, not folders:** the home card was sent to `ui`, which has no plan
step, while the same request said it needs a plan; the four `dev` folders are combinations of
independent properties, and asking for properties also shows when no folder has the right
combination. **The descriptions of the options are the program:** the engine card got "none of
these" because the READMEs say how a workflow runs, not when to use it. **The best answer may be
"this card is not ready":** catching a clarity of 1.35 before an implement session guesses is worth
more than the folder. **Unsure is an answer:** a split that flips between askings is a card the
person should see. The owner chose: the dispatcher reports what the work needs, and that reshapes the
folders.

### 2.5 Getting Things Done

The owner's older idea: GTD's diagram as the workflow. It is a fixed tree of closed questions, its
inputs are a person's raw notes with no schema, every decision precedes the work, a wrong answer puts
an item in the wrong list, and "unsure" has a home — the item stays in the inbox. Nine synthetic
captures, seven judgments each in one request: about 180 ms and $0.00003 a capture. The first run
misfiled three items, and both faults were the wording of two questions; Jev had answered exactly
what was asked. Reworded, rerun in seconds: the calls and replies became "do it now", the wishes
"someday / maybe", the unclear ones stayed in the inbox. Two projects were still misfiled, and that
was the order of the tree in code — with raw answers recorded, reordering re-sorts everything with
no new call. Jev stops at *writing* a next action (that is generation: a person or an LLM writes, Jev
can check), and at anything that depends on what is not in the note.

The parallel: this project is already GTD where "delegate" means a team of agents. Inbox cards are
captures; parked cards are someday / maybe; a plan as a folder of cards is a project; runs in flight
and gates are waiting-for; `wf decide` and the supervisor are the review; a card too small for a
workflow is the two-minute rule. The same system at two scales.

## 3. The vision, as the owner gave it

- **One inbox.** "Check my last 10 emails." "Draft an answer to the email from Morgan." "A new home
  page." The system picks the thing up and sends it to a team that can do it.
- **Smart decisions plus generation.** Typed judgment at the edges where a decision is needed;
  language models to do the work and write the text.
- **Not tied to code.** Today the system assumes a repository. Tomorrow code is one preset.
- **Two ways to have it.** Open source on your own machine; a hosted subscription for people who do
  not want to think about it. Presets — a GTD preset first — so that putting things in the inbox
  "just works". People who want to build their own can, and it has to be simple: create an agent,
  say what it is responsible for, put agents in a team.
- **The agent is the building block.** `review` and `implement` are agents, not steps.
- **A step stays, as a node.** Said by the owner on 19 September, settling "does a step still exist?": a
  workflow is a graph of logical nodes, and what is *attached* to a node does the work. Today that is
  an agent, and the node passes it a brief and data. Later it may be a script, an HTTP call, a typed
  judgment or a remote agent — anything a workflow tool such as n8n would put on a node. The code
  already has one node that is not an agent: `harness: check` is a script. Three things a step file
  mixes today come apart: *who* does the work (the agent: standing instructions, model, tools, the
  shape of its result), *where it sits* (the node: after whom, loop, check, gate), and *the job this
  time* (the brief, from the inbox card, never from a file). What makes it flow is typed data: what a
  node produces is its declared `output:`, what it is handed is its `input:`, whatever is attached.
- **An agent is an interface, not a file.** Three kinds, one contract:
  1. *defined here* — a markdown definition run on a harness this system controls;
  2. *native sub-agent* — run inside another agent's session, as Claude Code's `.claude/agents/*.md`;
  3. *remote* — an agent hosted elsewhere and reached over a protocol such as A2A, where only the
     contract is ours.
- **An agent may run agents.** The orchestrator and sub-agent pattern stays possible. It may well be
  a cost saving — a sub-agent that explores and hands back a conclusion keeps that exploration out
  of the parent's context, and §1 says re-read context is the bill. It has not been measured here:
  0 of 234 worker transcripts contain a sub-agent call.

**What the machine guarantees, whoever orchestrates.** The line is drawn at the edge of a task, not
around who plans. Every task has one budget, one set of tools it may use, one typed result, a record
of what happened, and a gate in front of anything that sends, spends or cannot be undone. Inside a
task an agent is free to orchestrate; the price is that its sub-agents' work is on no record, does
not survive a crash, and cannot be approved separately. Work that needs any of those is lifted to the
team. A middle way: an orchestrator whose only tool is "file a task", so its sub-agents are durable
tasks — a plan as a folder of cards is already nearly this.

## 5. What stays, and why it matters more now

- **Records are facts; the tick is level-triggered; one writer per file.** Unchanged.
- **The durable loop calls no model.** The written rule is "no LLM in a tick or in `wf decide`"
  (`docs/plan-hold-the-bar.md:973`). It is about the loop and the person's decision; it says nothing
  against an agent running agents. It entered on 12 September as a "not doing" from the evaluation
  against *how to hold the bar on production agent code*; the owner regards it as an optimisation to
  revisit on evidence, not a creed. If a typed judgment is ever admitted, this wording was proposed:
  a model's answer may exist only as a recorded fact — asked once by code outside any pass, journalled
  with its question, pinned model and probabilities under one writer, never re-asked for the same
  inputs, read from evidence whose author has no stake; it may label or order what a person sees, and
  moves nothing on its own until the owner decides otherwise, case by case and on measurement.
- **A person decides what leaves the machine.** `gate:` is already the mechanism.
- **Least privilege per agent.** Email is hostile text, and §2.3 measured that text steers a judgment
  when it is the only evidence. The agent that reads mail has no tool that sends; the drafter
  produces an artifact; sending is a separate, gated step. This is the product's safety story.
- **Prose is not a constraint; errors say what to do next; a guard is proven by a test that makes it
  refuse.** Unchanged.

work for folder runs, and the shipped `note` team (write → review) runs end to end with git stubbed out to prove it is
never called. The api and the board tolerate a run with no repo, base or branch. Still to file: the inbox and the board
for folder runs, a folder's lifetime, workspaces at the Factory's level, then P3.


### P3 — Capabilities, connections, and three classes of effect
An agent declares what it needs (`gmail.read`); a connection registry per person holds the tokens
(MCP servers are the transport; the task already carries `mcp`); every capability is *read*, *draft*
or *send*; *send* passes a gate. **Done means:** a read-only "last ten emails" team and a "draft a
reply" team run locally, and a test makes a send without approval refuse.

*What an agent says it can do, shipped 2026-09-19* (run `an-agent-says-what-it-can-do-l314`, this branch). The owner set the
reach plan above aside — "too much … just keep it simple" — and asked for the A2A Agent Card's shape instead. Read at the
source (`specification/a2a.proto`), A2A's `capabilities` are protocol features (streaming, push notifications), **not** reach:
what an agent can do is its `skills`, each `{ id, name, description, tags }` with optional `examples`, `inputModes`,
`outputModes`. So an agent file takes one new key, `skills:`, naming a `.json` list beside it — a sidecar, as `output:` is —
and the list shows up wherever the agent does: the Agents page, its own page and form, a step's page, `wf agents`, and
`wf agents card <name>` / `GET /api/agents/<from>/<name>/card`, which renders the A2A `AgentCard` JSON. A card for an agent
nobody can call over A2A is a description, not an endpoint, and it says so beside the card rather than in it: the card leaves
`supportedInterfaces` out — A2A marks it REQUIRED, and an interface would be a transport and a URL nothing here serves — and
what says why is `wf agents card`'s line on stderr and the api's `servedOverA2A: false` with its `why`. Deliberately not in this slice: no registry, no
connections, no enforcement — a skill fences nothing — no remote call, no new package, no `/.well-known/` URI. When P3 above is built, its reach keys want a name that is not
`capabilities`, or the two vocabularies collide.

### P4 — Kinds of verification
Beside the shell check: a schema check on the result, a typed judgment that reads facts code
fetched ("does this summary cite only the ten emails in the list?"), and a person's approval. Outside
code there is no test suite, so a typed judgment has no plain-code rival there; this is where Jev
earns its place. **Done means:** each kind is a recorded verdict the pass reads, never computes.

### P5 — The judge package, and the clarify layer
One package with Effect inside and a Promise facade: a live layer over the SDK, a recorded layer
(keyed by pinned model, question, options and state; a failure is a fact too), a replay layer for
hermetic tests, and a three-way `decide` whose `unsure` the caller must handle. Filed from the pass
as a task, like a check. The key stays out of `wf up`'s environment. On top of it, *clarify*: an
inbox item's properties in one request; code matches them to teams by "use this when" and by
capability. Start as a suggestion that gates nothing, beside a plain-code rival, to collect the
held-out data every experiment of §2 lacked. Read-only work may later start on a confident answer;
anything else waits for the person. **Done means:** each "never reads it" has a test that makes it
refuse.

*The owner, at the package's plan gate on 19 September.* Two things. Effect is welcome anywhere
inside this codebase where it fits, the workflows package included; the one condition is that a
consumer never has to adopt it, which a Promise facade keeps. And not everyone will have a Jev
subscription, so the judge is optional by design: later it is an agent in the agents list that is
off unless its criteria are met (a key in the environment). The package allows that — it imports
nothing from the workspace, nothing imports it, with no key every question reads `unsure`, and it
can say whether it is usable here without making a request.

*First slice merged 19 September (`f373830`, then `9d22a7c`; two rounds, $19).* `packages/agent-judge` and the `judge`
command. Each question has a key (pinned model, the exact question, a hash of the state) and a folder of write-once files;
the first whole answer to land is linked exclusively as `<key>/answer.json` and a read looks at that file alone, so a late
answer never moves a key; with no key nothing is claimed, written or built, and a key added later just asks. `judge status`
says `ready` or `off`. Live, on two of this plan's cards: P0.6 stayed in the inbox (planning first, P 0.74, unsure); agents
on the board went to `dev-planned-build`; each second asking made 0 requests. Not built: anything that calls it. The
thresholds are still unmeasured on held-out cards, and TypeSafe's retention terms are still unread.

*Measured the same night (`8e48a9b`, `06ab21a`; report in `experiments/jev/judge-runs-2026-09-19.*`).* `judge runs` scored
the 75 dispatches already made on the four `dev*` folders, beside a plain-code rival: 74 requests, 17 s, under a cent, no
failed answer. **The web property holds**: P 0.83, R 1.00, and every one of its six "false positives" was the person's —
work that changed an app, filed on a folder without `-build`; the rival's P is 0.71. **The plan question does not**: a
planned run reads a median 0.95, an unplanned one 0.64 with a quarter of them at 0.8 or above, and at 0.8 / 0.2 the judge is
unsure on 44 of 75 — so as a dispatcher it would have parked 46 of 75 cards, nearly all on that one question. It leans yes
on any long brief, which is also the owner's reading of that week (the statusline run reads 0.88). Before clarify gates
anything: keep web, and either default to a planned folder or reword the plan question and measure it again. The label is
agreement with a person, not accuracy; the planned folders exist only since 14 and 16 September, and since P0.6 a
`-build` folder no longer means "web". P3's place in this plan changed the same evening: the owner set aside reach and
connections (`plans/p3-reach-and-connections.md`) for an agent's configuration shaped after A2A's Agent Card, whose
`skills` — id, name, description, tags, examples — are also what a clarify layer would match a card against.

### P6 — Harnesses
A *light* harness — a model-and-tools loop on a small model — because "check my last 10 emails" must
not run inside a coding tool with a 25k-token prompt on opus. A harness billed by API key, because a
hosted service cannot run other people's work on one person's subscription. An *A2A* harness for
remote agents: as recalled, A2A's task states (submitted, working, input-required, completed, failed,
canceled, with artifacts) map almost one to one onto what the engine observes — check the
specification before building. Emission of native sub-agent files from agent definitions.
**And measure** orchestrator plus sub-agents against today's single session on the same card: cost,
peak context, outcome.

### P7 — A store interface; then tenants
Run records behind an interface, as the engine's `Journal` already is. Files stay the local default —
people can read them, which is part of trusting the system. Hosted: a database, tenants, auth, a
vault for connection tokens, a sandbox per person, and the subscription mapped onto the budgets that
already exist.

### P8 — Triggers
A schedule or an event files a card. A standing rule the person wrote is still their word.

## 7. The name

"hkb" is *the harness kanban board* (`README.md:3`). There is no kanban, and the product is not a
board. The name describes a screen the project is leaving behind.

**What a rename touches.** The repository and its directory; the root `package.json` name; the README
and `CLAUDE.md` titles; `packages/agent-engine/docs/hkb-migration.md`; mentions in `run.ts`,
`check.ts`, both packages' READMEs, `features.md` and `open-issues.md`; about ten test files in
`apps/api/test` that use the word in fixtures. **What it does not:** `agent-engine`,
`agent-workflows`, the `ae` and `wf` commands and the `~/.agent-workflows` store carry no trace of
it. **One trap:** Claude Code keys its per-project memory and transcripts by the checkout's path, so
renaming the directory orphans `~/.claude/projects/-home-yrnd1-projects-hkb-v2/`; move it with the
directory.

**What the name should say.** A system a person can trust with their work; an inbox in front of
teams of agents; neither "code", "board", nor a vendor's word. Candidates, none checked for a free
package name or domain: **Tickler** (GTD's tickler file, and the engine's own *tick*); **Steward**
(looks after things on your behalf); **Relay** (an inbox that hands work on); **Standing Order** (a
person's word that keeps being carried out). The owner's choice.
