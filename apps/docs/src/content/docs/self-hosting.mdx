title: Self-hosting
description: From a fresh Linux server to a factory's first run, started from your laptop, GitHub included.
---

This guide takes a fresh Linux server and gets your factories running on it, in order. You prepare the machine, put it on a private
network, install Nemia, open the board, connect the server to GitHub, point your laptop's `nemia` at it, apply a factory and start its
first run. [Install](/install/) explains what the installer does. This page links to it rather than repeating it.

It was first done on a VPS running Ubuntu 24.04 with 8 vCPU and 16 GB of memory. The commands below are the ones that worked there.
Where a command needs a value of yours, it is written in angle brackets: `<server>` is how your laptop reaches the server over SSH, and
`<address>` is the server's Tailscale address.

## 1. A machine and a user

Take a VPS that you reach with an SSH key and no password. As root, or as the provider's admin user with sudo, upgrade the packages
and install git and curl:

```bash
apt-get update && apt-get upgrade -y
apt-get install -y git curl
```

Nemia runs as a user of its own, not root. Add one that accepts the same SSH key, and let its services run while nobody is logged in:

```bash
adduser --disabled-password --gecos '' nemia
mkdir -p /home/nemia/.ssh
cp ~/.ssh/authorized_keys /home/nemia/.ssh/
chown -R nemia:nemia /home/nemia/.ssh && chmod 700 /home/nemia/.ssh && chmod 600 /home/nemia/.ssh/authorized_keys
loginctl enable-linger nemia
```

Check that the machine has cgroup v2, which the per-session memory limits need:

```bash
stat -fc %T /sys/fs/cgroup     # cgroup2fs
```

## 2. A private network

The board and the api are for you and your machines alone. Tailscale puts the server on a private network with your laptop.
Install it from Tailscale's own apt repository (the lines for Ubuntu 24.04), as root:

```bash
curl -fsSL https://pkgs.tailscale.com/stable/ubuntu/noble.noarmor.gpg | tee /usr/share/keyrings/tailscale-archive-keyring.gpg >/dev/null
curl -fsSL https://pkgs.tailscale.com/stable/ubuntu/noble.tailscale-keyring.list | tee /etc/apt/sources.list.d/tailscale.list
apt-get update && apt-get install -y tailscale
tailscale up --hostname=<name>
```

`tailscale up` prints a link. Open it in a browser signed in to your tailnet to add the server, then read its address with
`tailscale ip -4`. Your laptop joins the same tailnet with Tailscale's own app.

Then close the server to the internet with your provider's cloud firewall. Allow only these inbound:

- UDP 41641, Tailscale's direct path between your machines;
- ICMP.

Before you remove public SSH, check that `ssh nemia@<address>` works over Tailscale. From then on you reach the server only over
Tailscale. Port 8787, where the board and the api listen, is never opened publicly.

## 3. The install

Install as the Nemia user, over `ssh -t`, because the installer asks its questions on the terminal:

```bash
ssh -t nemia@<address> 'curl -fsSL https://github.com/emyann/nemia/releases/latest/download/install.sh | sh -s -- --bind <address>'
```

It asks three things ([Install](/install/#install) explains each one):

- **The Claude token.** Answer yes. Make the token with `claude setup-token` on a machine that has a browser and a signed-in Claude
  Code, then paste it at the prompt. It is not shown as you paste. [Your Claude token](/install/#your-claude-token) explains whose
  token a server may run on.
- **Start at login.** Answer yes. The installer sizes the service to the machine. The 8 vCPU, 16 GB server read as about 15.2 GiB and
  was sized to 6 sessions at once, each limited to 7.6 GiB: the limit is half the machine, a ceiling on one session and not its share.
- **The address to bind.** `--bind` already gave it the Tailscale address, so it does not ask
  ([Bind it to a private network](/install/#bind-it-to-a-private-network)).

Because the store is bound beyond the machine, the installer prints the first person token, once. **Write it to a file at once, and
paste it nowhere else**: no chat, no ticket, no log. Anyone holding it is you on the api.

You can always mint another token straight into a file on your laptop, without it ever being shown:

```bash
ssh <server> '~/.local/bin/nemia token add laptop' | sed -n 's/^Authorization: Bearer //p' > ~/.nemia-token
chmod 600 ~/.nemia-token
```

The installer links the command at `~/.local/bin/nemia`. A command passed to `ssh <server> '…'` runs in a shell that has not read your
profile, so `~/.local/bin` is not on its PATH. This page types the full path there. In a login shell on the server, add the
directory to your PATH once and type `nemia` alone:

```bash
echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.profile
```

## 4. The board

Open `http://<address>:8787` on your laptop and paste a person token once. The board keeps it in a cookie.

The browser marks the page as "Not secure" because the board speaks plain HTTP. The traffic between your machines is still encrypted,
because Tailscale tunnels it.

## 5. GitHub

A factory on GitHub pushes each run's branch with git and opens its pull request with the GitHub CLI
(`packages/templates/sdlc/carried/pull-request.ts`). The daemon clones a repository named by its URL with git too. All of it uses the
server's own credentials. **Nemia holds none.** So the server's Nemia user signs in to GitHub once, as below.

### The GitHub CLI

Install it from GitHub's apt repository. This needs root once:

```bash
mkdir -p -m 755 /etc/apt/keyrings
curl -fsSL https://cli.github.com/packages/githubcli-archive-keyring.gpg | tee /etc/apt/keyrings/githubcli-archive-keyring.gpg >/dev/null
chmod go+r /etc/apt/keyrings/githubcli-archive-keyring.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/githubcli-archive-keyring.gpg] https://cli.github.com/packages stable main" \
  | tee /etc/apt/sources.list.d/github-cli.list >/dev/null
apt-get update && apt-get install -y gh
```

The package installs the command in /usr/bin, which is on the service's PATH.

### Sign in, as the Nemia user

```bash
gh auth login --hostname github.com --git-protocol https --web --scopes workflow
```

`--web` signs in with a one-time code. The server has no browser to open and no clipboard to copy the code to, so the GitHub CLI warns
that it failed to copy the code and failed to open a browser, then prints the code and waits. This is the normal path on a server, not an error to fix. On any machine, open
[github.com/login/device](https://github.com/login/device), enter the code and approve. The command then finishes on the server.

The `workflow` scope lets a run push a change under `.github/workflows/`. Without it, GitHub refuses such a push. It is added to the
scopes the GitHub CLI always asks for, so `gh auth status` then lists gist, read:org, repo and workflow.

Then let git push over HTTPS with the GitHub CLI's token, and give the commits a name:

```bash
gh auth setup-git
git config --global user.name "<your name>"
git config --global user.email "<your email>"
```

`gh auth setup-git` makes the GitHub CLI git's credential helper for github.com, by its full path (/usr/bin/gh), so the daemon's
git finds it whatever its PATH. It fails while no host is signed in, so it comes after the sign-in. Every commit a step makes carries
that name and email. GitHub's noreply address (Settings, Emails) is one choice of email.

### A repository reached by SSH

If you would rather the server reach a repository by SSH, give it a key of its own for that repository. Make the key as the Nemia user,
and add its public half to the repository on GitHub as a deploy key with write access (the repository's Settings, Deploy keys):

```bash
ssh-keygen -t ed25519 -N '' -f ~/.ssh/id_ed25519
ssh-keyscan github.com >> ~/.ssh/known_hosts
cat ~/.ssh/id_ed25519.pub
```

Then name the repository by its SSH URL, `git@github.com:<owner>/<repo>.git`, when you add the factory. The clone's remote then is
that URL, and git pushes over SSH. The pull request is still opened by the GitHub CLI, so its sign-in above stays.

[A repository by its URL](/install/#a-repository-by-its-url) explains how the daemon clones and keeps a repository named by its URL.

## 6. The laptop

Install Nemia on your laptop as a client of the server, with the token file you wrote in step 3. The laptop must be on the same tailnet:

```bash
curl -fsSL https://github.com/emyann/nemia/releases/latest/download/install.sh | sh -s -- --client --server http://<address>:8787 --token-file ~/.nemia-token
nemia ls
```

The installer writes a context for the server and makes it the current one. From then on, the laptop's `nemia` drives the server: the
reads, the runs, the inbox, the decisions and every other verb about the store. [A client of another machine](/install/#a-client-of-another-machine)
explains contexts, and which verbs always act on the machine you type them on.

## 7. A factory and its first run

Apply a factory from a template, on the repository's URL. The server clones it with the credentials of step 5. Here it is the builtin
template, [sdlc](/sdlc/), set to judge and land its work on GitHub:

```bash
ssh <server> '~/.local/bin/nemia factory apply mill --template sdlc --set github=true --repo https://github.com/<owner>/<repo>.git'
```

With `github=true`, the factory waits on the repository's CI context, named ci unless you set another; [its parameters](/sdlc/#its-parameters)
say what else it reads. This one command runs on the server, over SSH, because a factory named by URLs is not yet filed over the api (below). A clone that
fails is refused with git's own words and the setup to do, and nothing is filed.

Then start its first run from the laptop:

```bash
nemia start "add a --quiet flag to the export command" --workflows quick --factory mill
nemia ls
```

The run works in a worktree of the server's clone. Its implement step pushes its branch and opens its pull request with the server's
GitHub sign-in, and the board shows the run step by step. [How a run lives](/how-a-run-lives/) follows it to its landing.

## Still by hand

Each of these has a card. Once a card lands, its line leaves this page.

- **The factory is applied over SSH.** The laptop's `nemia factory add` and `nemia factory apply` with every `--repo` a URL are not
  served over the api yet. Until they are, type the command on the server (step 7). Card: _api-a-factory-on-repositorie-1pyt_.
- **The quota panel has no answer.** The board's quota panel asks a Claude Code found on the api's PATH. A server with the release's
  Claude Code alone has none there, so the panel says the quota cannot be asked for. The sessions run all the same. Card:
  _runtime-the-quota-asks-the-c-m4cv_.
- **The first line of `nemia version` says 1.0.0 on v1.3.0.** The lines under it say the release you run. Main now reads the release's
  own version, which comes with the release after v1.3.0. Card: _release-nemia-version-get-ap-rhjd_.
