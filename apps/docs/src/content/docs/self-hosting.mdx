title: Self-hosting
description: From a fresh Linux server to a factory's first run, started from your laptop, GitHub included.
---

This guide takes a fresh Linux server and gets your factories running on it, step by step. You prepare the machine, put it on a
private network, install Nemia, open the board, connect the server to GitHub, point your laptop's `nemia` at it, apply a factory, and
start its first run. [Install](/install/) explains what the installer does, and this page links to it rather than repeating it.

We first did this on a VPS running Ubuntu 24.04, with 8 vCPUs and 16 GB of memory. The commands below are the ones that worked there.
Values you need to fill in are in angle brackets: `<server>` is how your laptop reaches the server over SSH, and `<address>` is the
server's Tailscale address.

## 1. A machine and a user

Start with a VPS you reach with an SSH key and no password. As root, or as the provider's admin user with sudo, upgrade the packages
and install git and curl:

```bash
apt-get update && apt-get upgrade -y
apt-get install -y git curl
```

Nemia runs as its own user, not as root. Add a user that accepts the same SSH key, and let its services run while nobody is logged
in:

```bash
adduser --disabled-password --gecos '' nemia
mkdir -p ~nemia/.ssh
cp ~/.ssh/authorized_keys ~nemia/.ssh/
chown -R nemia:nemia ~nemia/.ssh && chmod 700 ~nemia/.ssh && chmod 600 ~nemia/.ssh/authorized_keys
loginctl enable-linger nemia
```

Check that the machine has cgroup v2, which per-session memory limits need:

```bash
stat -fc %T /sys/fs/cgroup     # cgroup2fs
```

## 2. A private network

The board and the API are for you and your machines only. Tailscale puts the server on a private network with your laptop. Install it
from Tailscale's own apt repository (these lines are for Ubuntu 24.04), as root:

```bash
curl -fsSL https://pkgs.tailscale.com/stable/ubuntu/noble.noarmor.gpg | tee /usr/share/keyrings/tailscale-archive-keyring.gpg >/dev/null
curl -fsSL https://pkgs.tailscale.com/stable/ubuntu/noble.tailscale-keyring.list | tee /etc/apt/sources.list.d/tailscale.list
apt-get update && apt-get install -y tailscale
tailscale up --hostname=<name>
```

`tailscale up` prints a link. Open it in a browser signed in to your tailnet to add the server, then get its address with
`tailscale ip -4`. Your laptop joins the same tailnet with Tailscale's app.

Next, close the server to the internet with your provider's cloud firewall. Allow only these inbound:

- UDP 41641, Tailscale's direct path between your machines;
- ICMP.

Before you remove public SSH access, check that `ssh nemia@<address>` works over Tailscale. From then on, you reach the server only
over Tailscale. Port 8787, where the board and the API listen, is never opened to the public.

## 3. The install

Install as the Nemia user, over `ssh -t`, because the installer asks its questions in the terminal:

```bash
ssh -t nemia@<address> 'curl -fsSL https://github.com/emyann/nemia/releases/latest/download/install.sh | sh -s -- --bind <address>'
```

`--bind` puts the installer in server mode (like `--serve`). It then asks two questions ([On a server](/install/#on-a-server) explains
each), where a laptop install asks none. It asks nothing about a harness: you activate one afterwards
([Activate a harness](/install/#activate-a-harness)).

- **Start at login?** Answer yes. The installer sizes the service to the machine. The 8 vCPU, 16 GB server reported about 15.2 GiB,
  and was sized to 6 concurrent sessions, each limited to 7.6 GiB. The limit is half the machine: a ceiling for one session, not its
  share.
- **Which address to bind?** `--bind` already gave it the Tailscale address, so it doesn't ask
  ([Bind it to a private network](/install/#bind-it-to-a-private-network)). Without `--bind`, it lists the machine's private
  addresses by number. A public address, or every interface, is rejected unless you pass `--public`.

Because the store is reachable beyond the machine, every caller needs a personal token. The installer prints none. It creates the
server's own token directly in its local context, and prints a first-visit link for the board (step 4). It ends with `nemia doctor`,
which lists what is in place and the command that fixes each missing piece. The board's Setup page shows the same check.

You can also create a token directly into a file on your laptop, without it ever being displayed:

```bash
ssh <server> '~/.local/bin/nemia token add laptop' | sed -n 's/^Authorization: Bearer //p' > ~/.nemia-token
chmod 600 ~/.nemia-token
```

The installer links the command at `~/.local/bin/nemia`. A command passed to `ssh <server> '…'` runs in a shell that hasn't read
your profile, so `~/.local/bin` isn't on its PATH. That's why this page uses the full path there. In a login shell on the server, add
the directory to your PATH once, and then just type `nemia`:

```bash
echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.profile
```

## 4. The board

On your laptop, open the first-visit link the installer printed, `http://<address>:8787/?link=…`, within ten minutes. It signs that
browser in once, and the board keeps the token in a cookie that scripts can't read. `nemia board link` on the server creates another
link. With `--base` and the address your browser uses, it prints the link with that name, since a browser keeps one cookie per host
name. A store with no harness and no factory opens on the welcome page, which activates a harness and verifies it with two checks.
Alternatively, click _Pair this browser_ on the board's sign-in page, and approve the code it shows with
`nemia pairings approve <code>` on the server. From a laptop whose `nemia` has a context for the server, `nemia open` creates the link
on the server's store and opens it in the laptop's browser, at the server address the context names. The board stays signed in while
you use it: each visit extends it by thirty days, until you sign the browser out in Settings or revoke the token with
`nemia token rm`.

A browser without a token can only sign in at a name the store accepts: the loopback, the address it binds to, and, on a store marked
as exposed, the names you declare for it. Your tailnet name isn't the bound address, so declare it in the service's environment,
next to `WF_EXPOSED=1`. Separate several names with commas, without ports:

```bash
nemia service install --bind <address> --env WF_SERVED_NAMES=nemia.<tailnet>.ts.net
```

`nemia doctor` lists the names it accepts. A pairing or first-visit link opened at any other name is rejected, so a site whose name
points at your server can't sign in through it.

The browser marks the page as "Not secure" because the board uses plain HTTP. The traffic between your machines is still encrypted,
because Tailscale tunnels it.

## 5. GitHub

A factory on GitHub pushes each run's branch with git (`packages/templates/sdlc/carried/pull-request.ts`), labels and waits on its
pull request with the GitHub CLI, and opens the pull request through the GitHub MCP server, which the factory adds. The daemon also
uses git to clone a repository given by its URL. Git and the GitHub CLI use the server's own credentials, which **Nemia does not
store**, so the server's Nemia user signs in to GitHub once. You sign the GitHub MCP server in from the board's settings page by
typing a short code on GitHub's device page, with no address to copy. Nemia stores that token itself, refreshes it, and passes it to
each session.

The `sdlc` template's `build` and `quick` workflows declare these as needs, each with its fix. A run of either waits before its first
session while a need is missing, showing which one, and starts on its own once it is met. On the board's Setup page, or on the server:

```bash
nemia doctor fix gh --factory <factory> --workflow build
nemia doctor fix gh-sign-in --factory <factory> --workflow build
nemia doctor fix git-identity --factory <factory> --workflow build
```

The first command installs the GitHub CLI into `~/.agent-workflows/tools`, without root. The second signs it in with the `workflow`
scope and shows the one-time code separately, with the link to enter it. The third gives git the account's name and its noreply
address. The sections below do the same by hand.

### The GitHub CLI

Install it from GitHub's apt repository. This needs root once:

```bash
mkdir -p -m 755 /etc/apt/keyrings
curl -fsSL https://cli.github.com/packages/githubcli-archive-keyring.gpg | tee /etc/apt/keyrings/githubcli-archive-keyring.gpg >/dev/null
chmod go+r /etc/apt/keyrings/githubcli-archive-keyring.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/githubcli-archive-keyring.gpg] https://cli.github.com/packages stable main" \
  | tee /etc/apt/sources.list.d/github-cli.list >/dev/null
apt-get update && apt-get install -y gh
```

The package installs the command in /usr/bin, which is on the service's PATH.

### Sign in, as the Nemia user

```bash
gh auth login --hostname github.com --git-protocol https --web --scopes workflow
```

`--web` signs in with a one-time code. The server has no browser to open and no clipboard to copy the code to, so the GitHub CLI
warns that it couldn't copy the code or open a browser, then prints the code and waits. This is expected on a server, not an error.
On any machine, open [github.com/login/device](https://github.com/login/device), enter the code, and approve. The command then
finishes on the server.

The `workflow` scope lets a run push changes under `.github/workflows/`. Without it, GitHub rejects such a push. It is added to the
scopes the GitHub CLI always requests, so `gh auth status` then lists gist, read:org, repo, and workflow.

Then let git push over HTTPS with the GitHub CLI's token, and set a name for commits:

```bash
gh auth setup-git
git config --global user.name "<your name>"
git config --global user.email "<your email>"
```

`gh auth setup-git` makes the GitHub CLI git's credential helper for github.com, using its full path (/usr/bin/gh), so the daemon's
git finds it whatever its PATH. It fails if no host is signed in, so run it after signing in. Every commit a step makes uses that
name and email. GitHub's noreply address (Settings, Emails) is one option for the email.

### A repository reached by SSH

If you'd rather the server reach a repository over SSH, give it its own key for that repository. Create the key as the Nemia user,
and add its public key to the repository on GitHub as a deploy key with write access (the repository's Settings, Deploy keys):

```bash
ssh-keygen -t ed25519 -N '' -f ~/.ssh/id_ed25519
ssh-keyscan github.com >> ~/.ssh/known_hosts
cat ~/.ssh/id_ed25519.pub
```

Then use the repository's SSH URL, `git@github.com:<owner>/<repo>.git`, when you add the factory. The clone's remote is then that URL,
and git pushes over SSH. The GitHub CLI still opens the pull request, so you still need its sign-in from above.

[A repository by its URL](/install/#a-repository-by-its-url) explains how the daemon clones and maintains a repository given by its
URL.

## 6. The laptop

Install Nemia on your laptop as a client of the server. The laptop must be on the same tailnet:

```bash
curl -fsSL https://github.com/emyann/nemia/releases/latest/download/install.sh | sh -s -- --client --server http://<address>:8787
nemia ls
```

The installer pairs with the server. It shows a short code, which you approve on the server with `nemia pairings approve <code>` or
on the board's Setup page. A token named after your laptop is then saved, never displayed, in a context that becomes the current one
(`--token-file` still accepts a token file instead). Run the last command it prints to
[connect a coding agent](/install/#connect-a-coding-agent) to the server. From then on, the laptop's `nemia` controls the server: reads,
runs, the inbox, decisions, and every other command about the store.
[A client of another machine](/install/#a-client-of-another-machine) explains contexts, and which commands always act on the machine
you type them on.

## 7. A factory and its first run

From the laptop, apply a factory from a template, using the repository's URL. The laptop's `nemia` sends it to the server, whose
daemon clones the repository with the credentials from step 5. This example uses the built-in template, [sdlc](/sdlc/), set to check
and land its work on GitHub:

```bash
nemia factory apply mill --template sdlc --set github=true --volume https://github.com/<owner>/<repo>.git:rw
```

If the clone fails, the command is rejected with git's own message and the setup to do, and no factory is created. A `--volume` that
is a folder rather than a URL refers to a folder on the server, so the server rejects it from the laptop: run that one on the server.

On v1.4.0 and earlier, which only create a factory by URL on the server itself, run the same command there, as
`ssh <server> '~/.local/bin/nemia factory apply mill --template sdlc --set github=true --repo <url>'`, the flag those releases used.

With `github=true`, the factory waits on the repository's CI check, named ci unless you set another
([its parameters](/sdlc/#its-parameters)). [Before you apply it on GitHub](/sdlc/#before-you-apply-it-on-github) lists what the
repository needs first: the GitHub CLI signed in on the server, which step 5 did, and a base branch protected to require that CI
check, so a pull request only merges once it passes.

Then start its first run from the laptop:

```bash
nemia start "add a --quiet flag to the export command" --workflows quick --factory mill
nemia ls
```

The run works in a worktree of the server's clone. Its first worktree installs the clone's dependencies (about a minute for an npm
repository), and you install nothing by hand ([A repository by its URL](/install/#a-repository-by-its-url)). Its implement step pushes
its branch and opens its pull request with the server's GitHub sign-in, and the board shows the run step by step.
[How a run lives](/how-a-run-lives/) follows it to its landing.
