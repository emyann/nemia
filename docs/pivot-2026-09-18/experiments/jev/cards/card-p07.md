The subscription's quota on the board: a statusline script writes what Claude Code knows, the api reads it, and the Factory shows how much is left and when it resets

This is P0.7 of docs/pivot-2026-09-18.md (§1, *Visibility*). The owner's first complaint on 2026-09-18 was not knowing how much of the Claude subscription was used or left while workers drained it. Claude Code knows: the JSON it hands a statusline command on stdin carries `rate_limits` — `five_hour` and `seven_day`, each with `used_percentage` and `resets_at`, and on some plans `seven_day_sonnet` and a `spend_limit` — beside `subscription_type` and the session's `context_window`. Verified 2026-09-18 by reading the 2.1.277 binary; it is absent for API-key sessions (`rate_limits_available: false`). A statusline runs only in an interactive session's terminal, so the numbers are as fresh as the owner's last interactive turn, and nothing else on this machine exposes them. Verify all of this yourself against the installed `claude` before building on it — read its docs with the claude-code-guide knowledge you have, or print a real statusline payload — and record what you found, with the version, in features.md.

Read CLAUDE.md (the apps/web lines; *Something beside the Factory's floor that mounts after its first render narrows a floor already fitted*: load what it draws in the route's loader and fit again when it comes or goes; one writer per file; the e2e's rules), then apps/api/src/app.ts (how the Factory's header numbers are served, how the home store's root is found), apps/web/src/routes/index.tsx and the Factory's header, apps/web/src/lib/api.ts, apps/web/test/e2e/run.ts and seed.ts, and packages/agent-workflows/src/runner.ts (`HOME`, `$WF_ROOT`).

1. A statusline script, shipped in this repository (propose where; it is run by Claude Code, not imported by a package), that reads the payload on stdin and writes the quota part of it to ONE file in the home store — `$WF_ROOT/quota.json` or a name you justify — atomically (write beside, rename), with the time it was written and the Claude Code version. It is the file's only writer. It prints a short status line of its own (the two percentages and the nearer reset), and if the owner already has a statusline command it can wrap it: run it with the same stdin and print its output first. It must never fail a session: any error prints nothing and exits 0. Node only, no dependency.

2. Do NOT edit the owner's `~/.claude/settings.json` or any file outside the workspace. Write the exact `statusLine` block a person adds, in the README, and say how to check it works. A later session installs it on the owner's word.

3. The api serves what the file says and how old it is, and says plainly when there is no file, when it is stale (older than a bound you choose and state — a number from yesterday must never read as now), and when the plan has no limits to show. It reads the file on request; it keeps nothing in memory that outlives the file.

4. The Factory's header shows it, small and legible in both themes: the five-hour window and the week, each as a percentage used with its reset time in the person's own time zone, the age of the reading, and a plain sentence for the three empty cases with what to do. A window past a threshold you choose is marked. Load it in the route's loader so the floor is fitted once, and fit again if it comes or goes.

5. The e2e seeds a quota file, draws the header in both themes, then the stale case and the missing case, and puts the store back. A unit test covers the script: a real-shaped payload in, the file out; a payload with no `rate_limits`; a wrapped command; an unwritable store — and in every case exit 0.

Not part of this change: predicting spend; pausing or throttling runs on quota (say in features.md, in three lines, what a run-level guard would need — the owner may want "do not start a run above 90%" later); tokens and dollars per step, which P0.4 already shows.
