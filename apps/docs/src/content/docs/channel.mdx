---
title: Follow the feed from an agent
description: Push Nemia's feed into a Claude Code session as it happens with nemia channel, or follow it from any MCP client through the API's resources.
---

Nemia's feed has one line for each thing that happens: a run starts, a step waits for a person, an agent's call is refused. `nemia
watch` prints it in a terminal. This page shows how to put it in front of an agent instead. A Claude Code session can have it pushed
in as it happens, and any MCP client can follow it from the API. Both see the same thing: the Event list the API serves
(`GET /api/events`), one Event per line, filtered by the same label selectors as `nemia watch -l`.

## From Claude Code: `nemia channel`

`nemia channel` is a local MCP server that Claude Code starts over stdio. It declares itself a channel (a Claude Code feature in
research preview) and sends each Event as a notification, which the session reads as a tag. The Event's message is the tag's body,
and each of its fields is an attribute: `reason`, `involved_kind` and `involved_name`, `type`, `source`, `at`, `resource_version`,
and, when the Event has them, `namespace`, `waits`, `on`, `via`, `call`, and `try`. It is one-way: it offers no tools and accepts no
reply. The body is text a person or an agent wrote, so the channel tells the session to read it as data, not as an instruction.

Add it to the project's MCP servers, in a file named .mcp.json at the project's root:

```json
{
  "mcpServers": {
    "nemia": {
      "command": "nemia",
      "args": ["channel", "-l", "waits=person", "--cursor-file", "/home/you/.nemia-channel-cursor"]
    }
  }
}
```

Then start an interactive session with the channel loaded:

```bash
claude --dangerously-load-development-channels server:nemia
```

Channels only reach interactive sessions: a session started with `-p`, or through the Agent SDK, gets no notifications. In a Team or
Enterprise organization, an administrator must turn channels on first, with the channelsEnabled setting.

- **Which events.** `nemia channel -l <selector>` takes the same selectors as `nemia watch -l`. Repeat the flag to add more: an Event
  comes through if any one matches. `-l waits=person` sends every line that waits for a person, and `-l team=core` the lines of runs
  with that label. With no selector, every Event comes through. `nemia channel -n <namespace>` limits it to one factory's Events.
- **Which store.** Like every `nemia` command, the channel reads the store of the current context: this machine's daemon (started if
  it isn't running), or a server's. To follow a server's store, set the context for the channel alone in the entry's environment,
  `"env": { "NEMIA_CONTEXT": "<context>" }`, next to `args`.
- **Where it starts.** Without `--cursor-file`, the channel starts from now each time Claude Code starts it. With
  `nemia channel --cursor-file <path>`, it saves the position of the last line it sent in that file. When it starts again, it sends
  what was written while it was stopped, each line once. It sends at most 50 of those lines (`RESUME_MOST`). Beyond that, it sends a
  single notice instead, saying how many lines it skipped, the `resource_version` they start after, and the command that prints them.
  That command is `nemia watch --once <resource_version>` in the channel's context (`NEMIA_CONTEXT=<context>`, so it reads the same
  store), with the channel's selectors quoted (and, for a namespace, its factory). A person can type it in a terminal, and the
  session's agent can run it through its shell. Then the channel continues with new lines.
- **What it says about itself.** A tag with a `notice` attribute comes from the channel itself:
  - `skipped`: the lines beyond the cap.
  - `missed`: the saved position couldn't be resumed because the feed was replaced, so it started over from now.
  - `down`: the channel lost the API. It says only what it saw, and never guesses a cause such as sleep, the network or the server.
    If its own clock jumped (the channel did not run for a while), it says so with both times, for example "The channel did not run
    from 9:22 PM to 9:52 PM (its clock jumped 30 min)". Otherwise it says it has had no answer from the API since a given time. It
    retries every second and loses no line.
  - `up`: the API answers again. The notice says how many lines were written in the meantime and after which `resource_version`.
    It says whether the server's daemon restarted in that time ("restarted at 9:40 PM" or "did not restart"), as the feed's
    `DaemonStarted` lines show, whatever the channel's selectors. It also lists each run and step among those lines that waits for a
    person, one per line. Its attributes `caught_up`, `after`, `restarted` (`yes`, `no`, or `unknown` when it could not be read) and
    `restarted_at` say the same for an agent.

    Times are in the local time of the machine the channel runs on. When the channel can't tell the time zone, it uses UTC and says so.

  - `refused`: the API rejected a selector or a namespace. The channel stops with exit code 2 and explains why on stderr too.

## From any MCP client: the API's resources

For clients other than Claude Code, Nemia's MCP port serves the Event lists as resources: `nemia:///api/events` for every Event, and
`nemia:///api/namespaces/<namespace>/events` for one factory's. Each takes selectors in its query, like the API's list, as in
`nemia:///api/events?labelSelector=waits%3Dperson`; repeat the parameter to add more. Reading one (resources/read) returns an Event
list as JSON. It holds the newest Events the port has seen for it while a client follows it, and its `metadata.resourceVersion`, the
feed's position, from which `nemia watch --once <resourceVersion>` continues. A client on MCP's 2026-07-28 revision follows a
resource by sending a subscriptions/listen request that lists it among its resource subscriptions. The port then notifies the client
each time a matching line is written, and the client reads the resource again.
