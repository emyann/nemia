A workflow is how a team works on a card: which steps there are, who does each one, in what order, what gets checked, and where a
person decides. It is a folder of Markdown files, and each file is one step. The orchestrator, `packages/agent-orchestrator`, reads
it and runs it.

**It owns** the order of the steps and what each step is allowed: its agent, its tools, its check, its gate, and its budget.

**It never touches** whether the work is good. That is a judgment, made in a step by an agent or measured by a check, never by a
condition in the workflow.

**Its entry point** is the folder itself. A repository keeps its workflows checked in, one folder each inside a `workflows` folder at
its root, the same way it keeps its CI. Your own workflows live under `~/.agent-workflows/workflows/` (`WF_ROOT`). Nemia ships no
built-in workflow: a factory's workflows belong to it, written by the people who run it.

## A step

A step is one Markdown file. Its frontmatter configures it, and its body is its brief: what the step is asked to do.

```md
---
after: implement
agent: reviewer
loop: implement
rounds: 3
budget: 16
---

Review the changes on this branch. Be specific about correctness, not style.
```

The keys are a fixed list. Before anything is spent, the orchestrator rejects any key it doesn't know, by name
(`packages/agent-orchestrator/src/workflow/step-file.ts`). The main ones:

- `after` lists the steps that must finish first. Steps run in that order.
- `agent` names who does the work: an agent defined once, in the `agents` folder next to the workflows (see [Agents](/agents/)).
- `check` is a command that measures the work.
- `gate` makes a person approve before anything after the step starts.
- `loop` and `rounds` send the work back for another round.
- `budget` caps what all of the step's tries may cost together.
- `workspace` sets which folder the step works in: by default, a worktree of the run's own, or else the repository's checkout.

The frontmatter is YAML, and every value is read as the text you wrote. Quote a value that contains `: ` or ` #`, or that starts with
a character YAML treats specially (such as `[`, `{`, `*`, `&`, or `-`), as in `check: "grep -q 'status: done' out.md"`. Write a long or
multi-line check as a literal block: `|-`, with the command indented on the lines below it:

```md
---
after: implement
check: |-
  npm run typecheck &&
  npm test -- --grep "review: findings"
gate: true
---
```

A key that takes a list, such as `after`, accepts both `plan, design` and `[plan, design]`.

The folder's `README.md` is not a step. It describes what the workflow is for, and the board shows it.

**No key is control flow.** There are no conditions, no expressions, and no templating. "Is this good enough?" isn't something a
workflow language can evaluate. It is a judgment, and a judgment belongs to a step with an agent in it. A workflow describes a team,
not a program.

## The closeout

Every step ends by signing off with a structured answer, its closeout, in a versioned envelope (`apiVersion: "nemia/v1"`). It holds:

- an `outcome`: `done` or `blocked`;
- a one-line `summary` for the person who decides;
- a Markdown `body` for everything else;
- the `artifacts` it made: files, or named values such as a pull request's URL;
- what it `needs`, only when blocked.

A workflow can ask a step for more fields with `output`, on top of its agent's own, each field declared once. A later step reads them
with `input`, as data. Once a step signs off, the run saves its whole closeout as a file named closeout.json in the step's files
directory, where later steps read it. Claude Code returns the answer through its `StructuredOutput` tool, and Codex through its
output schema. When a step signs off `blocked`, everything waiting on it stops, and the person is told.

The board displays each field of `output` according to its schema: text, a list, a table, a yes or no, or a number. A field can name a
shape instead of a schema, `{ "x-shape": "<shape>", "description": "…" }`. The run expands the shape to its schema before the harness
reads it, and the board displays the field as that shape:

- `questions`: questions a person answers by choosing among options, on the board or with `nemia retry --message`.
- `budgets`: the spending caps a gated step proposes for the steps after it (see _What a step may spend_).
- `link`: a URL, or null for none, shown as a link.
- `commit`: a commit hash, or null for none, shown as the commit.

## The check

The run doesn't take the agent's word that the work is done. A step's check is a command the run executes after the step signs off,
in the step's own workspace.

- Exit 0 means `verified`, and the next step starts.
- Any other exit means `failed (check)`, and nothing waiting on the step runs.
- A step with no check shows `unverified`, so it is never mistaken for a step someone checked.

The command comes from the folder as it was when the run started, frozen on the run's record. A check added to the folder later, even
by a step, never reaches the run. Only a check that finished counts as a verdict on the work. A check killed at its deadline, or
stopped, says nothing about the work, and you can run it again with `--recheck`.

## Trying again

When a check fails a step, `retries` sets how many times the run sends the work back on its own. It continues the same session and
tells it why. You can also retry a step yourself with `nemia retry`: continue the session with a message, start fresh, switch to
another model, or just run its check again.

A check can fail for reasons unrelated to the work: the machine ran out of memory, or a test is flaky. In that case, the continued
session changes nothing and signs off as before, and the run runs the check again, up to the `retries` limit. If the session instead
signed off blocked, with nothing committed since the check failed, you can run that check again with `nemia retry --recheck`. The run
compares the commit the check judged with the branch's current commit, and accepts the result only if they match.

A check can also declare which exit codes mean a failure only you can resolve, such as a tool that isn't signed in. This is its check
failure policy. It works like a Kubernetes Job's pod failure policy: rules are read in order, and the first one that matches decides.
On such an exit code, the run doesn't retry on its own and uses up no try. The step waits for you, and once you have resolved it,
`nemia decide` offers to run its check again.

## A loop and its rounds

A review step can send the work back. Its `loop` names an earlier step to run again, and `rounds` caps how many times (3 by default).
After each round, the reviewer's closeout sets `again` to yes or no:

- `again: true`, with rounds left: the next round starts. The earlier step continues its session and receives the reviewer's
  findings as data. It answers each finding: fixed or not, and why.
- `again: false`: the loop is done, and whatever waits on it starts.

When the rounds run out, a person decides, with one of the two commands that answer a waiting step. Either one more round
(`nemia retry <run> --round`), or enough (`nemia approve <run> --message "…"`), which accepts the work as it is. The old commands,
`nemia round` and `nemia accept`, still work and print the new one, until a later release removes them.

## A gate

A gate is a property of a step: `gate: true`. When the step signs off, nothing after it starts until a person approves. While it
waits, the step shows `awaiting approval`, holds no slot, and spends nothing.

- `nemia approve <run> <step> --message "…"` lets the run continue. The message reaches the next step as data.
- `nemia retry <run> <step> --message "…"` sends the step back with an objection, and it waits at its gate again.

You can also add a gate when you start a run (`--gate <step>`), or on a card.

## The landing

The end of a run is a step too: its workflow's last one. In a workflow that lands on a branch, that step stages the merge. It runs in
the repository's own checkout (`workspace: base`) and has a check. It also either has a gate, or waits on a step that can send the
work back: a review, whose `loop:` closes on the work.

1. A person approves the gate. Or, when the last step has no gate, the review before it passes, and the run starts the step itself.
   A workflow whose last step has a check but neither of these is rejected when the folder loads: its check would commit to the base
   branch without anyone's approval.
2. The step's agent stages a merge of the run's branch into the base branch, without committing it, and signs off with the commit
   message.
3. The run executes the check on the merged code. On exit 0, it commits the merge. On any other exit, it aborts it (`landEnding` in
   `packages/agent-orchestrator/src/ending/ending.verb.ts`, on `landingDue`).

Nothing in the packages assumes what shipping means. Another workflow's last step might open a pull request, or be a study that a
person accepts.

## What a step may spend

`budget` is in dollars: the most all of a step's tries may cost together, across every try and every round. Past it, the step shows
`over budget`, and the run starts nothing more for it on its own. A person raises the cap with `--budget` on `nemia retry`, adding
`--round` for a round. The cost is the price the harness reports for each attempt, read by the runtime once the attempt ends.

A gated step can propose budgets for the steps after it, as data: an output field with the budgets shape (`"x-shape": "budgets"`),
with one item per step, giving its name, its amount in dollars, and why. Approving the gate turns them into those steps' caps,
including any amount the person changes while approving (`--budget` on `nemia approve`, once per step). When a step has several caps,
the first that applies is the one it runs under:

1. a person's `--budget` on `nemia retry`, for the step's current try;
2. the most recent approval that set it a cap;
3. the step's own `budget`.

If a proposed cap is higher than the step's own `budget`, the gate says so, next to the amount the workflow gives it. Nemia at `auto`
never approves such a gate on her own: a person must.

A factory can set a cost line per workflow: what a run of that workflow should stay under, including every try and round of every
step (`nemia factory cost-line set <factory> <workflow> <usd>`, or the board's factory settings). A run keeps the line it started
with. At a gate with budgets, the most the run can cost is what it has already spent plus what each step's cap still allows. If that
exceeds the line, the gate says so, on the board and in `nemia decide`, and Nemia at `auto` never approves that gate on her own. With
no line set, or with caps at or under it, nothing is shown. The line doesn't cut anything: a step's own cap still ends its session.

## An example

The `sdlc` template's `build` is a workflow, `packages/templates/sdlc/workflows/build/`: design, then implement, then review (which
loops back to implement), then land. Its steps are `packages/templates/sdlc/workflows/build/design.md` (gated),
`packages/templates/sdlc/workflows/build/implement.md` (with a check), `packages/templates/sdlc/workflows/build/review.md`
(`loop: implement`, five rounds), and `packages/templates/sdlc/workflows/build/land.md` (in the checkout, started by the review's pass,
with no gate). A factory copies it from the template as its own. It isn't built into Nemia.
