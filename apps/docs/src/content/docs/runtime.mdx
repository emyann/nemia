The runtime runs one agent session on one harness, durably, and knows nothing else. It lives in `packages/agent-runtime`, and its
command is `ae`. Everything on this page lives there.

**It owns** how a session runs: the brief, the harness it runs on, its command, its mounts, its deadline, and its restarts. It also
owns each task's journal and attempts, and admitting queued tasks under a limit.

**It never touches** a second workload. Anything that knows about two sessions, such as "implement, then review", a board, a gate, or
a budget across tries, belongs to the layer above: the orchestrator. The runtime's own README calls this its boundary
(`packages/agent-runtime/README.md`, _Where this stops_).

**Its entry points** are two: `agent-runtime` (`packages/agent-runtime/src/index.ts`) and `agent-runtime/vocabulary`
(`packages/agent-runtime/src/vocabulary.ts`), the harnesses' vocabulary, with nothing that reads or writes. The orchestrator reaches it
through one client, `packages/agent-orchestrator/src/runtime-client.ts`.

## A task

A task is a brief submitted to run on a harness. It is the runtime's unit of work: what you ask for, written down before anything
runs. A task holds its brief, the folder it runs in, the harness, and the harness's own arguments in one object, its `config`
(`HarnessArgs`, in `packages/agent-runtime/src/harness/args.ts`). The runtime passes `config` to the harness without reading it.

## An attempt

An attempt is one start of a task's session. Each start creates one attempt, and however the attempt ends settles the task:

- `succeeded` when the harness finished it.
- `failed` when it failed, was lost, couldn't start, or ran out of time.
- `stopped` when someone asked it to stop.

The runtime never retries on its own. Whether to try again, and whether to continue the same conversation or start fresh, is a
judgment about the work, so it belongs to the caller. To continue, a caller submits the task again with `resumeFrom`, naming the
session to continue. In a workflow, the orchestrator does this.

## A harness

A harness is the program a session runs in. The runtime has three built in, chosen per task: `claude` (Claude Code, every session on
the Agent SDK), `codex`, and `command`, a plain process. A remote agent at an address is a fourth kind. The runtime reaches all of them
the same way, over A2A (see [A2A](/a2a/)). To add your own harness, declare it with a `HarnessSpec`.

## The engine

The engine is the loop that makes each task happen. It compares two things:

- **What you asked for**: the journal. It is one append-only file per task, one event per line, and only the runtime writes it.
- **What the machine is doing**: what the harness reports. That is the sessions it holds, and what each one is doing.

The two are linked by a name the runtime chooses, `ae/<task>/<attempt>`, which every session gets when it starts. On each pass, the
engine reads both, asks one pure function, `decide` (`packages/agent-runtime/src/core/domain.ts`), for the one thing to do, and does
it. No decision is made anywhere else: `decide` holds all of the runtime's judgment.

**The engine never holds a session.** A job runs in a process the engine detaches. A long-lived session is held by the daemon's
holder, and a later holder can resume it. Either way, the session outlives the engine. You can stop, upgrade, or restart the engine
in the middle of a three-hour session, and it picks the session up on its next pass.

**It is level-triggered.** Each pass reads the world, decides, and acts, and carries nothing over to the next pass. `tick` runs one
pass, and `up` runs `tick` on a timer. Because a single `tick` can drive a task to its end, no state hides in the process
(`packages/agent-runtime/README.md`, _`tick` and `up`, and why both_).

## A job and a long-lived session

By default, a task is a **job**: its session runs to the end, and the task settles when it does. A workflow's steps are jobs.

A task submitted with `restartPolicy` set to `Always` is a **long-lived session**. It stays open between turns, and only a stop ends
it. On Claude Code, it runs attached, inside the process that holds the runtime's sessions (the daemon). Without the daemon, it can't
start. Between turns it is idle (`idleOf`): nothing happens and nobody is asked anything. `say` sends it its next message. If it ends
without anyone asking it to stop, it starts again on the same conversation. The wait before restarting starts at 10 seconds, doubles
for each end in a row, and is capped at 300 seconds. [Nemia](/nemia/) runs this way.

## Admission

A task submitted as `queued` waits for permission to start. Permission can come from two places:

- **`admit`**, given for one task by name (`ae admit <id>`).
- **The engine itself, under its limit.** `maxConcurrent` sets how many sessions of each pool can work at once. When a slot frees up,
  it goes to the waiting task with the highest `priority`, then the earliest submitted, then the lowest id. Nothing running is stopped
  to make room. One pure function makes this choice: `toAdmit` (`packages/agent-runtime/src/core/admission.ts`).

An engine can be marked `unschedulable`, like a Kubernetes node. While it is, nothing queued starts, and work already running
continues. The orchestrator submits every step's task as queued, with its run's momentum as the priority, and gives the engine its
limit.

**Admitting a tool call is a different thing.** A task's `callAdmission` names a command that is consulted before some of its
session's tool calls. It answers allow, ask the person, or deny (`packages/agent-runtime/src/harness/admission.ts`). This is about one
call inside a running session, not about whether a task starts. [Nemia](/nemia/#what-she-is-allowed-to-do) is fenced this way.

## The lifecycle of a task

A task moves through this statechart. Its states are A2A's task states, plus three of the runtime's own: `starting`, `stopping`, and
`ending`. The diagram is drawn from the code, `packages/agent-runtime/src/core/lifecycle.ts`, which `decide` uses as a function and
never runs.

```mermaid diagram=lifecycle

```

How to read it:

- A task is `submitted`, waits while it is queued, then goes through `starting` to `working` once its session starts.
- When a session ends, the task goes to `ending`, where the attempt's end is recorded. It then settles as `completed`, `failed`, or
  `canceled`.
- A task held open for a person waits in `input-required` (`holdOpen`) until the person answers or closes it.
- When a person stops a task, it goes to `stopping`, and settles as `canceled` once nothing is left open.

The guards in brackets choose between two edges for the same event. `holds` sends a held task to wait for a person. `live` stops a
session still running past its deadline. `lastDone`, `endedDone`, and `endedStopped` choose how a task settles. A person's actions,
`requestStop`, `answer`, and `close`, are declared next to the machine (`VERBS`), since no pass takes them.

What a person sees of a task is its phase, one word from a fixed set (`TaskPhase`). While the task is unsettled, the phase is
`pending`, `starting`, `working`, `quiescent`, `needs-human`, `input-required`, `idle`, `restarting`, `between-attempts`, or `ending`.
Once settled, it is the outcome: `succeeded`, `failed`, or `stopped`. For an attempt in progress, a view also carries the session's
own state, in A2A's terms (`session`).
