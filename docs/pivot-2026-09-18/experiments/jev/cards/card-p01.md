A loop's target keeps one closeout schema for the whole run, so continuing its session never rebuilds the prompt cache — agent-workflows

Measured 2026-09-18 over 73 resumed sessions (docs/pivot-2026-09-18.md §1, Finding 2; the scripts are docs/pivot-2026-09-18/experiments/cost/resume.py and verify.py): all 29 continuations filed with the same closeout schema as the session they continued reused the prompt cache, writing 5–20k tokens. All 43 filed with a different one rewrote the whole conversation — 200k to 640k tokens each, at twenty times the price of reading them: 14.1M tokens, about $134 in six days. The cause is `closeoutSchemaOf(step, owesReplies(steps, run, r.step))` (src/run.ts, called from src/runner.ts where a try is filed): a loop's target is filed without `replies` in round 1 and with it from round 2. The schema becomes Claude Code's `StructuredOutput` tool through `--json-schema`, a tool definition sits at the very front of the cached prompt, and a changed tool invalidates everything after it.

Read CLAUDE.md, then src/run.ts (`closeoutSchemaOf`, `CLOSEOUT_SCHEMA`, `REPLIES_SCHEMA`, `LOOP_REPLIES`, `owesReplies`, `roundOf`, `owedFields`, `parseCloseout`, `declaredOutput`, `roundAsk`, `roundLines`, and how a closeout's extra fields travel to the steps that ask for them), src/runner.ts (every call of `closeoutSchemaOf`: a first filing, a retry, a round, `respond`), packages/agent-workflows/docs/features.md's account of `loop:` and `replies`, and the tests beside them.

What to change:

1. A loop's target is filed with `replies` in its closeout schema on EVERY try, the first round included. `closeoutSchemaOf` decides that from the frozen workflow alone (is this step some step's `loop:` target?), never from the round the run is on. In round 1 the target was handed no findings and answers `replies: []`; `REPLIES_SCHEMA`'s description says so, in a sentence the agent will read. What is OWED does not change: from round 2 a non-empty `replies` is owed exactly as today, by the same machinery, and an empty list in round 2 is refused as a missing one is today.

2. Round 1's empty `replies` goes nowhere: it is not a declared output, it is not handed to the looping step or to any `input:`, and `wf decide` does not print it. Pin that with a test.

3. The invariant, as machinery rather than a comment: every task this package files with `resumeFrom` carries the same `closeoutSchema`, byte for byte as JSON, as the task whose session it continues — and the same `model`, `effort`, `tools`, `disallowedTools` and `permissionMode`, since each of those changes the cached prompt too. Add a test over the shipped folders (dev, dev-build, dev-planned, dev-planned-build, ui) that walks a run through a first try, a nudge, a round 2, a round 3 and a `respond`, collects what was filed, and fails on any difference within one session's chain. Give it a fixture that has the OPPOSITE first — a loop's target in round 2 — and check it fails without your change: CLAUDE.md, "a rule about order or names is not proven by a fixture that already has it". If some continuation legitimately differs, do not smooth it over: say which, why, and what it costs, in your closeout.

4. A run already in flight when this lands was filed in round 1 without `replies`. Its next round pays one cold resume, once; nothing is migrated. Say so in features.md.

Not part of this change: the engine; any other closeout field; `--autocompact` or a context cap (another run has it); agents and teams.
